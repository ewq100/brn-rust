## Gate 2 — failed qualification; headless evidence complete for this slice

All windows below use `gpui_kit::TestAppContext` and Kit's test platform. The BRN
Read comparison uses the actual pinned `TextViewState`/`TextView` implementation
and reproduces BRN's two literal-HTML plugins and inert link/image callbacks in a
[test-only host](tests/common/mod.rs). It does not import `brn-desktop`, duplicate
BRN's workflow, access its database or call providers.

### 1. Byte offsets — passed on the tested plain-source fixtures

Keyboard selection starts at a byte offset and advances by the editor's grapheme
navigation. Public input-handler selections are UTF-16; the host converts them
back to UTF-8 boundaries against the exact current string. Text is not searched
for a replacement occurrence after selection.

| Witness | Exact selected source bytes |
|---|---|
| Second identical `Identical paragraph.` | `22..42` |
| Second `tere` in BRN's `tere tere õun` family | `5..9` |
| `õun — ÕÄÖÜ šž` | `10..32` |
| Second decomposed `a` + U+0308 | `11..14` |
| Second `👩🏽‍💻` grapheme (modifier + ZWJ) | `23..38` |
| Second `Same 🦀.` after CRLF paragraphs | `29..39` |

Loading retained these exact source bytes, including CRLF, and select-all returned
the complete original byte interval for each. This does not prove all CRLF paint/
clipboard behavior: stock clipboard paste explicitly normalizes CRLF/bare CR to
LF. The math-load exception in check 5 also limits any general fidelity claim.

### 2. Programmatic edits and Undo — passed characterization; host work required

- `replace_range(5..9, "teine")` changes `tere tere õun` to `tere teine õun`,
  notifies observers, and emits **zero `EditorEvent::Changed`**.
- Undo restores the prior text; Redo restores the replacement. **Neither emits
  Changed either.** A following typed `!` emits one Changed and is a separate undo
  step; undoing it leaves the programmatic replacement intact, still silently.
- `set_text` emits no Changed and clears **both Undo and Redo**. Subsequent undo/
  redo cannot recover the old document or its typed edit.

BRN cannot attach draft persistence/generations only to Changed: local Undo/Redo
would silently change its visible buffer. An adapter must recognize actual text
changes, explicitly coordinate programmatic formatting and local undo actions,
and preserve dirty/base/generation guards. Observer notification alone also fires
for display/selection changes, so compare buffer contents before marking dirty;
it must never imply Save. Avoid `set_text` for unchanged display refreshes.
Durable BRN Undo remains a checked compensation through its service. Local editor
history must be reset/rebased at intentional document/revision transitions so it
cannot recreate stale drafts after Apply or durable Undo. No production adapter
or BRN Undo integration was implemented here.

### 3. Read-only wrapper — failed

There is no public built-in read-only switch. The test wrapper captures raw keys
and all exposed mutation actions. It blocks typing and the tested delete/newline/
indent/format/Undo shortcuts, including **Cmd-V**.

That is insufficient: calling the public `EntityInputHandler::paste` callback
still inserts `PASTED`, and `replace_and_mark_text_in_range` still inserts marked
`õ`; each emits Changed. Those are the input callbacks available to the platform,
not proof from a real native IME. A headless mouse click on the rendered task
checkbox also changes `- [ ] task` to `- [x] task` while the wrapper is enabled.

Thus a key/action wrapper around a selectable live Zorite editor does **not**
block every user edit. This does not prove every conceivable wrapper impossible.
Hiding the editable surface behind BRN's existing Read view would avoid exposing
it, but would not qualify Zorite itself as a selectable read-only/review editor.
Post-edit restoration is not a safe equivalent: text/events/history have already
changed. Central library mutation guards or comprehensive input/mouse mediation
need separate design and qualification.

### 4. Geometry — passed the bounded headless check

`bounds_for_offset` is unavailable before first paint. After layout it returns a
**zero-width caret box**, not a range rectangle. At byte offset 232:

| Layout | Caret top | Caret height |
|---|---|---|
| Width 800, text 16 | 92.8 px | 23.2 px |
| Width 240, text 16 | 255.2 px | 23.2 px |
| Width 240, text 24 | 556.8 px | 34.8 px |

A separate fixture renders an actual margin-comment element at the paragraph
start; after resize/rewrap it follows the new caret top (layout rounds to the
nearest physical pixel, within 0.5 px). The API reads the **last paint's** cache:
the host uses another frame after rewrap to position its overlay. A production
host needs explicit invalidation/scheduling and window-to-container coordinate
conversion. This proves a useful primitive for capability (a), not comment
collision layout, range rectangles, scrolling, folding or native usability.

### 5. Live WYSIWYG / BRN Read agreement — failed

With `set_markdown_style`, keyboard selections of known source intervals still
index the intended occurrences. BRN Read's source-to-rendered mapping returns the
same visible words for the heading/bold/repeated/Unicode/CRLF fixtures, and its
select-all returns the exact complete Markdown source.

**Actual pointer selections differ at hidden emphasis boundaries.** Using the
caret boxes to hit-test and drag across the visible word yields:

| Same fixture / visible word | BRN Read pointer source range | Zorite pointer source range / quote |
|---|---|---|
| `## Café 🦀` + `A **formatted** paragraph.` | `19..28` | `19..30`, `formatted**` |
| Second `täpne` in the repeated CRLF/combining/emoji fixture | `40..46` | `40..48`, `täpne**` |
| Second plain `echo` after `First **echo**.` | Source interval `38..42` maps to visible `echo` | `38..42`, `echo` |

The BRN comparison really dispatches pointer drags to its Read widget and checks
`selected_source_range`; the repeated fixture also distinguishes its first
`14..20` occurrence. No suffix trimming, fuzzy quote relocation, parser patch or
source adaptation was added to hide the Zorite result.

**Loading also changes source silently, even before styling is enabled:**

```text
input:  "before $$x^2$$ after"
loaded: "before\n$$x^2$$\nafter"
```

The Changed count stays zero. BRN Read retains the original source. Published
`normalize_loaded` is called by both `with_text` and `set_text`. Loading a reviewed
candidate therefore cannot currently preserve its exact byte identity in the
editor; the first later edit could also persist that normalization as draft text.

Zorite's Markdown scanner plus `zorite-markdown::syntax` is an additional
interpreter, not an implementation of BRN's established Read policy. This slice
finds concrete mapping/source-fidelity differences, not full CommonMark/GFM,
HTML/link/asset safety, formatting round-trip or visual parity qualification.

### 6. IME — API check passed; native quality pending

The editor implements `EntityInputHandler`: UTF-16 selection/text access, marked
range, unmark, replace/commit, replace-and-mark, bounds-for-range and point hit
testing. Its element registers `ElementInputHandler` during paint. A direct API
witness after `õ 🦀 ` composes `に🦀` with UTF-16 mark `5..8` and caret `8..8`,
then commits `日本` and clears the mark. Marking and commit each emit Changed.
`bounds_for_range` can span one wrap row; it is not a general range geometry API.

This checks the interface and its coordinate convention only. It establishes
nothing about real AppKit candidate placement, Japanese/Chinese/Korean/dead-key
input, cancellation, composition Undo, focus transitions or native selection.
Those remain gate 3 work.

## Stock result versus adaptation ideas

**Stock result:** compatible build; useful caret geometry; unacceptable unqualified
read-only/review and live-WYSIWYG source behavior for BRN. No stock library file
was edited and no adapted editor was built.

**Unapproved ideas only:** an explicitly assigned editor maintainer could propose
(1) a central read-only guard covering input callbacks, actions, checkbox/context
menu/widget writes; (2) lossless load behavior; (3) a deliberate hidden-delimiter
mapping contract aligned with BRN; and (4) a host text-change/local-Undo adapter
that preserves draft generations and durable Undo. Required tests include the
counterexamples here, input-handler paste/marked text, mouse mutations, exact
candidate identity, stale drafts and local-versus-durable Undo. A future proposal
must name its owner, bounded patch, upstream path and maintenance obligation.
No such adaptation/owner assignment is approved by this report, and no broad
GPUI/Rust upgrade or application fork is warranted.

## Capability decision and remaining risks

| Target | Result now | Recommendation |
|---|---|---|
| (a) Range geometry for margin comments | Caret anchor/layout primitive **passed** headlessly; no range rectangles | Promising for a later bounded host trial; scrolling/folding/multiple comments/native pixel geometry remain pending. |
| (b) Live WYSIWYG Markdown | **Failed** source mapping agreement and lossless-load witnesses; read-only wrapper also failed | Keep current production editor. Resolve these before any cutover or candidate display. |
| (c) macOS IME | API surface **passed**, native behavior **pending** | Do not infer usability from the callback test. |

**Is gate 3 worth running now? No, as an adoption gate.** Its native work cannot
resolve the already reproducible source/read-only failures. If a separately
approved bounded adaptation resolves those and a draft/Undo adapter is qualified,
the geometry primitive and successful stock graph make gate 3 worth revisiting.
Long-document latency/memory, scroll/fold/font/first-layout behavior on real fonts,
full Markdown/safety parity and native clipboard/IME remain explicit residual
risks. No editor adoption or writing-milestone completion is claimed.
