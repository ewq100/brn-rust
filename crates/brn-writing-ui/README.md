# BRN writing UI

`brn-writing-ui` provides a reusable writing panel, its transient note and review coordination, and presentation helpers for BRN desktop hosts. It is a UI component crate, not an application service or a standalone owner of workspace data. Its module boundary is visible in [`src/lib.rs`](src/lib.rs): the default feature set exposes toolkit-free formatting, tracked-change and layout helpers, while `native-ui` enables the GPUI-backed panel, document views, workbench, Markdown controls, components and theme. `native-test-support` adds GPUI test support; the `writing_host` example also requires `native-ui`.

The panel composes three different kinds of state. [`NoteLifecycle`](src/note.rs) tracks which note is open, its write/read presentation and its active edit session. [`ReviewLifecycle`](src/review.rs) tracks the exact candidate shown, comparison or editing mode, and selection; it prevents a dirty or partial review from applying the old candidate. These are transient coordination state. The GPUI [`WritingPanel`](src/native.rs) holds editor entities, selection, focus-facing controls and view state. GPUI owns text input, selection and IME mechanics; the host connects editor events to the lifecycle.

`Workspace` from `brn-threads-app` remains the service boundary for current records, versions, comments, recovery buffers, candidate preparation and checked apply. Its SQLite store is authoritative for saved notes, edit guards and recovery; presentation helpers never become a second Markdown or persistence authority. See the [architecture overview](../../docs/architecture/overview.md) and [invariants](../../docs/architecture/invariants.md) for these ownership rules.

A host owns and admits the `Workspace` context, supplies the current records, history, candidates and recovery buffers to [`WritingView`](src/native.rs), and dispatches panel requests through the shared app/service operations. Connect editor Change events to `note_changed`, and use the panel's Save, refresh and navigation operations so current visible input is sampled before publishing or replacing it. The host also handles recovery/discard choices, access changes and visible errors. Rejected or stale writes must leave the owner’s visible text available for comparison; hosts should use checked `Workspace` operations rather than write canonical SQLite state directly. The disposable [`writing_host` example](examples/writing_host.rs) shows this wiring with synthetic data; its [host](examples/writing_host/host.rs) owns the workspace and callbacks.

Before a non-explicit note replacement, the lifecycle rechecks its local recovery session against the checked store and refuses replacement if that buffer changed or closed; explicit same-note Recover still adopts the validated current buffer.

For component changes, consult the [verification guide](../../docs/development/verification.md) and choose evidence for the affected boundary. Widget or state checks do not establish native interaction quality; the guide describes the separate native qualification limits.
