# BRN architecture and reuse reassessment — 2026-10-07

**Status: evidence-backed recommendation, PROPOSED architecture; no implementation/adoption approval.** The [dated owner amendment](../product/BRN_PRODUCT_VISION.md#owner-amendment--2026-10-07) is accepted task authority. This report distinguishes requirements, observed code and proposed changes. The [ordered plan](../work/active/architecture-reassessment/plan.md) is the single change-plan handoff. Historical audits remain observations of their own trees.

## Recommendation

Retain the Markdown/assets vault, SQLite operational store, disposable retrieval, selected-provider Rig transport, AppWorker and exact reviewed recoverable application. Replace the expansion strategy of handwritten format interpreters with a small common intake/extraction seam and maintained format libraries. Make AI investigation and draft revision substantially more capable before approval. Keep the apply engine initially; do not make conversion-library adoption depend on recreating every existing refusal or generated byte.

Preferred **evaluation direction**, not accepted production dependency: a native BetterOffice Office adapter plus dedicated `mail-parser` MIME ingestion, with a separately qualified PDF adapter. Keep rdocx as the closest DOCX challenger; keep Docling as an optional subprocess challenger for layout/PDF/visual-heavy documents. A small combination can be simpler to install and maintain than either a universal engine or eight custom parsers. The measured probes below justify a focused end-to-end adoption slice, not whole-format fidelity claims. Narrow alternatives if the remaining acceptance scenarios fail; no compulsory rewrite.

The highest user costs are unavailable conversion of normal documents, approval before useful analysis, truncated context with no continuation, restricted proposal revision, and proof-heavy review that still does not show all meaningful content. Generic recovery code is large but serves concrete loss/stale-write failures; line count alone is no reason to remove it. Converters must never acquire authoritative write or cleanup authority.

## Proposed end-to-end architecture

1. **Intake:** user supplies files/content/URLs. Preserve exact originals and byte hashes once. Email attachments are children of their email evidence, not unrelated imports; generated IDs are BRN identities, never invented Message-IDs.
2. **Extraction:** run a selected format adapter in a disposable working directory with only supplied inputs. Reuse its upstream model; return Markdown/text, ordinary assets, locators, converter/version/settings and explicit omissions. A small result envelope is sufficient; do not invent a comprehensive Office/email/PDF IR.
3. **AI investigation/enrichment:** use the same Rig lane and explicit provider/model. Inspect original/page/image previews, compare extraction paths when useful, follow evidence, search approved current knowledge, propose relationships/actions/resolutions and revise drafts. Every attempt consumes visible configurable budget; cancel terminates local work and reports upstream cancellation uncertainty.
4. **Drafts/proposals:** save private work and immutable extraction snapshots. Distinguish originals, extracted observations, inferred normalization and proposed current knowledge. A revised destination/member/evidence set is a new reviewed version. Unchanged targets retain their captured before bindings. New targets get fresh host observations. If an existing target changed externally, preserve the stale binding until explicit reconciliation produces a newly displayed before/after; never reuse stale full replacement text with a silently refreshed fingerprint. Do not overwrite approved source evidence to “correct” interpretation.
5. **Human review:** show one understandable evidence-linked batch with independent consequences where useful and coherent dependencies where necessary. Partial conversion has prominent known gaps. The owner can revise/reject/approve the exact displayed set; mechanical conversion itself needs no approval.
6. **Approved application:** existing workflow validates permission, target/before/evidence/version bindings and applies recoverably. Converters/LLM never install vault files or approve their own work. Cleanup is a separate recoverable owner operation and unavailable for incomplete conversion.
7. **Retrieval/history:** index only appropriate saved approved knowledge for Current; retain explicit Source/History access, original evidence, derived assets and versioned snapshots. Recovery replays saved output, never an old model call or a converter re-run to regenerate lost history.

Use one intake seam, one AI runtime and one proposal/approval path. During migration the old converter may remain a named legacy format reader for existing records, not a competing default engine or hidden fallback. Compare versions in isolated evaluation; production selection is explicit. Existing receipts already preserve candidate payloads; preserve those readers. Conversion proof validation in [inbox_source.rs](../../crates/brn-store/src/work/inbox_source.rs) currently reconstructs literal-text preservation and hardcodes format wrappers; generalize future records to immutable artifacts rather than require exact current converter bytes. This is conditional schema design, not an instruction to migrate now.

### Execution isolation to evaluate

A subprocess alone is not a sandbox. Pass only one copied input/tree, bounded output directory, no inherited credential variables or provider caches, no vault handle and no network by default. Enforce wall time, total expanded bytes/parts/output, nesting and process-tree cancellation externally; in-process parse limits alone cannot interrupt every parser. Do not execute macros/scripts, fetch HTML/CID external URLs or load remote relationships automatically. Render HTML with scripts/network disabled and sanitized navigation. Use supported macOS process/resource/sandbox facilities and measure the packaged configuration before calling it isolated. Keep stage9 web fetching as explicit network-capable evidence capture, not converter network access. No general-purpose plugin or policy framework is justified.

Timing instrumentation includes JSON/debug conversion where stated.

This is a combined three-parser graph, not an incremental product build measurement. Rust-only deployment avoided Python/models in this probe. BetterOffice is young (0.x packages); its available corpus claims do not replace BRN acceptance tests.

### EML sources

Do not equate a UTF-8 pasted email or Markdown email with `.eml` support. A useful adapter must retain exact raw RFC 5322 bytes; decoded/ordered headers (including Message-ID/References and date timezone), the MIME tree and alternative bodies; charset and transfer-encoding diagnostics; original decoded attachment bytes, content IDs and source-part identities; nested `message/rfc822` messages. Render remote images as references without fetching them. AI may decide which alternative/body/attachment matters and propose grouping/thread links; extraction must keep enough evidence to revise that choice.

**Docling's pinned implementation is real EML:** `docling_slim-2.134.0/docling/backend/email_backend.py` imports Python `mailparser`, parses bytes, converts HTML through the HTML backend and normalizes MSG into the same route. However, `_get_attachment_labels` explicitly surfaces **attachment metadata only**, excluding encoded payload/content. Its Markdown/JSON export alone therefore does not satisfy BRN original attachment preservation. This is source inspection, not executed Docling behavior. [Pinned backend source](https://github.com/docling-project/docling/blob/v2.134.0/docling/backend/email_backend.py).

**Source-inspected newer release:** `mail-parser = 0.11.9`, MIT OR Apache-2.0, exposes `MessageParser::parse`, raw message, MIME parts, body alternatives, `MessagePart::contents`, nested message, `MimeHeaders::content_id`, raw offsets and `is_encoding_problem`. Write a small evidence adapter around it instead of MIME grammar. Its published version differs materially from current repository main: 0.11.9 does **not** expose the newer advertised `max_parts`/`max_depth` or lazy-decoding API. Keep an input cap and process budget; evaluate malformed/deep MIME behavior before selecting it. Published source has a fixed three-level transfer-encoded nested-message recursion limit. [Versioned API](https://docs.rs/mail-parser/0.11.9/mail_parser/), [published source](https://docs.rs/crate/mail-parser/0.11.9/source/). The source-research helper did not execute MIME; the lead executed 0.11.8 below. Keep these version scopes separate.

Kreuzberg's pinned email path retains optional attachment data and can recursively extract attachment/nested-message children. Its high-level evidence rendering uses `cleaned_text`, so confirm signature/quotation handling and source associations rather than assuming that cleaned prose preserves the email. It may be a useful comparison implementation while the direct MIME adapter supplies authoritative originals.
