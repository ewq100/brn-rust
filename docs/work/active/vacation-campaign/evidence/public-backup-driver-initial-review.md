Locations: adapter `38,260–272,402–403`; imported harness `37,131–143`.

The adapter creates `Public backup interruption qualification · Ω`, then calls `harness.note_bytes(source_snapshot)`. Its otherwise-valid fixture therefore necessarily raises `synthetic Note was not found in records` at the first extraction, after seeding the fresh workspace and before creating even the earlier complete backup. Use one explicit consistent fixture identity for creation and both extraction calls, without editing the preserved reviewed harness. This is a driver wiring defect, not a failed backup product witness.

### P2: Do not use exact SHM preservation as a canonical source-data gate

Locations: adapter `161–175,276–282,409–412,430–434` and implementation's source-sidecar preservation claim.

`sqlite_storage_snapshot` includes `-shm` bytes/hash/presence in the dictionary later required to be exactly equal across public CLI opens and read-only SQLite snapshots. SHM is SQLite's transient wal-index/reader coordination, not canonical data. The bundled SQLite source explicitly describes it as reconstructible and truncated/zeroed on last close (`sqlite3.c:67571–67587`); its reader marks may be changed by readers (`67799–67823`). Thus a legitimate open/read/close sequence can fail this gate despite an unchanged canonical DB, marker and all logical rows. This is source-established overconstraint, not a claim that a local run has already exhibited a sidecar change.

Keep the selected exact DB/marker and complete logical schema/row comparisons. Treat volatile SHM identity as diagnostic only. Make WAL handling explicit as well: WAL can contain authoritative pages, but ordinary checkpoint/unlink lifecycle is not automatically data loss. Preserve meaningful source-data checks rather than asserting a blanket immutable sidecar lifecycle. Update the implementation/receipt descriptions to the actual acceptance boundary.

### P2: Ensure standalone-output acceptance cannot consume companion WAL

Locations: adapter `289–294,398–407`; imported harness `63–84`.

The final checks validate a regular final DB and its size, then call `readonly_snapshot`, which uses SQLite `mode=ro` and query-only. Read-only mode still permits reading committed pages from a matching companion WAL. No check before that read establishes that the published DB is self-contained, and neither its sidecars nor journal-mode independence are checked. A WAL-dependent final output could therefore satisfy schema/all-row/Note equality while the claimed standalone backup (and its DB-only size bound) remains unproven. The earlier complete backup is accepted through the same gap.

Current production source deliberately switches the staged target to DELETE journal mode and closes it before publication (`backup.rs:89–108`); that is the product guarantee being qualified, not evidence supplied by the driver's current `mode=ro` comparison. Add a narrow read-only standalone acceptance check for both complete and retried outputs, ensuring the comparison cannot obtain required data from companion WAL. This may be an explicit no-companion-WAL/self-contained read check; it does not require production hooks, SQL repair, a new general validator or another interruption attempt. Avoid treating volatile source SHM preservation as a substitute.
