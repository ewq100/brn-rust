## Why private preservation is broader

A chat-owned copy with the same source chat can be private and accessible in its original scope. That does not settle a shared document displayed from a different Project, a project-owned Note, moved membership, or a deleted destination. Core `context.rs:22–41` uses `project_document_ids` for project-owned document admission. Merely setting `chat=Some(project)` does not put a new Note in that Project's documents. `ProjectCommand::CreateDocument` correctly groups the new Note and Project.documents change and fences affected context (`projects.rs:525–553`), but its command/intent has no source Note/base/current input. Calling it after an app-only privacy read leaves a source race and loses the desired source binding.

Preserving the original chat can also put a copy outside the Project the owner is currently using. Choosing source scope, displayed Project, every sharing Project, or a new independent destination is a product decision, not a visibility rule to guess. Managed assets/import/source relationships add further duplication obligations. `keep_in_brn` intentionally promotes the original and carefully preserves its related material; it neither copies visible edits nor supplies the intended semantics here. Do not reuse it as a hidden preliminary step.

Therefore defer private duplication explicitly. A later selected private-copy outcome needs destination/access semantics and an atomic source-bound checked operation that maintains the appropriate membership/provenance. No new owner decision is required to stop the current silent generalization while keeping text recoverable. An owner choice would be needed before choosing ambiguous shared-project copy behavior.

## Smallest sound shared boundary

A narrow owner-facing `Workspace` recovery-copy operation can reuse existing Store services without a new general framework, schema, or UI privacy authority. It should accept stable host intent containing source Note ID, the actual visible edit's basis version, exact proposed title/text, and captured displayed writing scope where applicable. The service resolves source records itself; a passed UI `Record` or `is_private` bool is not authorization.

For a new uncommitted attempt:

1. Read the exact stored source revision at the basis version; require a genuine usable general Note. Reject a private historical basis even if the current Note was explicitly retained in BRN later. Missing/wrong-kind/malformed revisions fail rather than falling back to the current Record.
2. Read the current source Note; require active, unsuperseded, general state. Resolve/admit the current writing context using the existing shared context rules where context is part of the call; refuse a captured private/project scope or a currently private/unavailable scope. Do not infer scope from an arbitrary selected chat or solely from project links. The existing `active_writing_context` explicitly distinguishes those from the working Note's actual admitted scope.
3. Create only the new plain working Note from the exact visible UTF-8 title/text. Keep historical provenance to the actual basis with `RevisionInput::Historical`, and a **separate Current input at the current version observed by this attempt**. If basis and current version coincide, retaining the necessary provenance/precondition need not create a new deduplication abstraction. Existing current-input handling supports multiple expectations for a source.
4. Use the existing immutable owner preparation and checked Apply. At `store.rs:2330–2352`, Current inputs are validated in the writer transaction before grouped effects; `current_input_matches` rejects a changed, archived or superseded source. Thus a privacy/version change after the service read cannot commit a general copy using its earlier observation. The historical revision is immutable and its existence is separately checked. No UI precheck alone closes this race.

**Do not make Current refer to the old edit basis merely because it is the source of text.** The intended action recovers public stale edits. A public source at version 2 must be allowed to produce a copy of edited text based on public version 1. Bind version 1 as historical provenance and observed version 2 as the mutable eligibility precondition. Reject only if the relevant eligibility changes again before Apply; do not automatically chase a new version after a failed intent.

This guards the actual historical basis and current source, not every version the Note ever had. An unbounded history/privacy-taint scan is neither needed for the stated binding nor selected here. If an “ever private” policy is desired, that is a separate contract choice. The narrow service is not a content-understanding proof that arbitrary owner-supplied text contains no private facts.

## Intent, replay, and editing state

Bind a stable host key to a digest of source ID, basis, captured context, and exact title/text before effect preparation, using `allocate_bound_operation`. The new identity remains derived from that operation. An identical completed retry must return its original receipt before mutable source/privacy checks, after verifying the same bound intent. A later source change must neither manufacture another copy nor invalidate proof that the earlier copy already committed. A changed source/basis/context/text under the same key must refuse. Preserve immutable prepared input versions on an incomplete retry, or refuse safely; do not silently replace a prepared request with freshly observed versions. Existing checked prepare/apply/replay supplies these mechanisms; no generic retry subsystem is needed.

The UI must capture the correct historical version. `load_note` can place the **latest current Record** beside recovered text whose `EditSession.base_version` is older. The visible recovered edit's basis is that session base, not automatically `open.record.version`. Conversely `BlockedElsewhere.base_version` is another session's hint, not necessarily the basis of this window's visible local text. The present dirty-stale button requires an owned session, so its captured session base is directly available; do not broaden this repair merely to support another lifecycle route. A future clean/blocked route must bind its actual visible origin deliberately.

Refusal must leave visible editor text, original Note/revisions, kept buffer bytes/generation/holder, open selection/context, and recovery access intact. A notice such as “This edit belongs to private work. It remains recoverable; saving a separate private copy is not available here” states the limit without claiming publication or directing the owner to promote the original. Do not discard/reload the edit or show the success notice on failure. Avoid overwriting a newer durable buffer merely to make a refused copy attempt look synchronized. Operation allocation itself may be durable; the promised refusal is no new Note/accepted copy receipt and no alteration of existing content/recovery, not necessarily zero database bookkeeping.

On allowed success, preserve the original kept edit exactly as the current action promises. A plain recovery derivative need not masquerade as a full imported Note or clone import confirmation/source relationships. Record its real basis through derivation inputs; retain original immutable import/provenance unchanged. Asset/link cloning and private import duplication remain outside this repair.

## Proportionate boundary evidence

Before implementation, select one focused real UI regression extending the existing public dirty-stale SaveCopy route with a reachable private working Note. The old source should fail at the intended privacy/no-general-copy assertion, rather than at an invented control API. After repair, invoke the same actual control and assert clear refusal, unchanged visible text/current canonical source/kept buffer, and no created general Note or copy receipt. Keep the existing public stale-copy positive assertion; it must still create exactly the visible text after the saved public version advanced. No native result follows from headless controls.

At the shared service boundary, include distinct cases that the existing general UI witness does not cover:

- private historical edit basis with a now-general source still refuses;
- general historical basis with a now-private current source refuses;
- general basis older than the current general version succeeds, preserving exact Unicode bytes and recorded historical/current versions;
- missing/archived/superseded/wrong-kind source refusal preserves canonical/recovery state;
- unchanged-key lost-response/reopen retry produces the same receipt/identity after a later source change; changed intent under that key refuses.

Current-input race protection should be demonstrated with existing genuine checked Prepare/Apply/two-connection seams if exposed by the selected API, and reused core current-input tests plus inspection that the actual recovery request carries the right Current input. Do not invent a broad hook/framework solely for this race. A direct app check that captures only Historical provenance is insufficient, even if both before-call privacy tests pass. The existing core current-input suite already proves changed-source rejection and coexistence of historical/current expectations; it does not prove the new service chose the right versions, which the new boundary witness must assert.

No new private-copy availability/export success is claimed when the selected implementation refuses it. Existing private search/export/Keep/Undo journeys remain reusable for the underlying privacy contract. Focused service/UI assertions plus affected existing core/app/writing/desktop checks and ordinary source review are appropriate; no provider call, private owner data, native launch, blanket per-keystroke DB poll, new persistence authority, or duplication/publication feature is justified by this assessment.
