## Why this boundary, and what it can establish

`SearchIndex::open` (`search_index.rs:366–393`) already owns admission, branding, schema/config validation and reconstruction of this disposable mirror. `inspect` (`1212–1283`) currently checks the raw SQLite header/application ID, `quick_check`, schema version/object names and expected metadata before returning `Usable`. `open_locked` then returns `Opened::Existing`, or rebuilds through existing immediate-transaction DDL. Core remains authoritative.

SQLite documents that `quick_check` omits index-to-table consistency. Its FTS5-specific command checks external content only with `rank=1` and reports discrepancies as `SQLITE_CORRUPT_VTAB`. These are different checks, so successful `quick_check` does not establish FTS/external-content correspondence. This supports the hypothesis, not an empirical claim that the pending fixture passes every existing check. [SQLite quick_check](https://www.sqlite.org/pragma.html#pragma_quick_check), [FTS5 integrity-check](https://www.sqlite.org/fts5.html#the_integrity_check_command).

All **four** schema lanes are external-content FTS5 tables: `fts_exact` and `fts_stem` index `passages.indexed_text`; `fts_message_exact` and `fts_message_stem` index `messages.text` (`search_index.rs:88–106,136–154`). Existing test helpers already issue the correct rank1 command separately for Note lanes (`tests/search_index.rs:52–61`) and Message lanes (`663–672`). Reuse that SQLite mechanism; ordinary `PRAGMA integrity_check`, rank0, testing one lane, or comparing `SELECT count(*)` through the external-content virtual table is not an equivalent proof.

The app's `sync` returns immediately for equal workspace identity/watermark (`search.rs:1397–1409`). Visibility/version rechecks cannot restore a missing candidate. Hence canonical changes and query result guards cannot substitute for admission health. Conversely, admission-only recovery does **not** promise detection of silent external mutation made after an index has already been admitted and kept open. The selected witness must distinguish those scopes; a mutation of a live cached connection followed by an ordinary query alone is not an admission regression witness.

## Smallest correctly owned recovery policy

Keep the current ownership ordering: reject symlink/foreign/unbranded-nonempty paths before any FTS special INSERT or reconstruction; allow existing missing/empty/interrupted-creation and old schema/config handling to follow their established paths. Only a current branded schema with matching metadata should reach all-four-lane external-content verification. Do not run current lane commands against older schemas or turn failed ownership admission into disposable data.

A confirmed logical FTS mismatch should produce **`Found::Rebuild` / `Opened::Rebuilt`**, clear the derived sync state through the existing full reconstruction, and allow the ordinary canonical full sync to repopulate Notes, Messages, links and scopes. The search worker already resets its dense cache for Created/Rebuilt (`search.rs:689–697`); do not preserve an `Existing` label after resetting passage IDs.

This must be a **narrow error classification**. Bundled SQLite defines the relevant FTS corruption result as `SQLITE_CORRUPT_VTAB`; rusqlite exposes its primary code as `DatabaseCorrupt`. The current broad `inspect` catch (`1272–1280`) maps primary `DatabaseCorrupt` to **`Found::Replace`**, which unlinks DB/WAL/SHM. Simply inserting rank1 checks with `?` immediately before `Usable` would therefore silently choose replacement. Classify the supported FTS discrepancy at its check site before that broad physical-corruption policy. Preserve the existing physical corruption recovery policy; propagate busy/locked, permission/read-only, I/O, cancellation and other operational failures rather than diagnosing them as corruption or returning an empty result.

Reusing the complete in-place reconstruction is preferable to a bespoke FTS-only repair: it has established metadata/watermark reset, canonical resync and dense-cache signaling. It preserves the file identity for existing readers instead of unlinking an otherwise readable SQLite file. No canonical write, new schema version, new recovery authority, format migration or generic generation framework is needed for this outcome.

## Concurrency and revalidation

The existing `search.lock` serializes BRN **open/rebuild**, not every write: already-open `SearchIndex::apply` uses a SQLite `Immediate` transaction and `Changes.base`, without taking that advisory lock (`search_index.rs:423–432`). Holding only `search.lock` is consequently not a complete writer freeze. Preserve both existing mechanisms; do not introduce a second lock hierarchy or assume the advisory lock protects all SQL writers.

The robust narrow admission decision uses the **current admitted connection under a SQLite write transaction**, with branding/schema/meta revalidated there before the four checks, and avoids using a stale inspection as permission for later destructive work. An immediate transaction avoids an upgrade race while a supported special INSERT checks FTS. The existing in-place rebuild transaction is the natural reuse point when the disposition is rebuilding. If an implementation first detects mismatch on the disposable inspection connection, revalidate that decision after acquiring the SQLite write transaction before rebuilding; do not blindly act on the earlier classification after closing/reopening. Fresh consistent state may be admitted rather than unnecessarily erased. This is a placement requirement, not a request for a new concurrency framework.

Every FTS command must operate against a consistent SQLite view of its external content and FTS data. A legitimate atomic `apply` must not look corrupt because content and index were read across a racing update. Locks/busy errors must leave the file intact and remain visible. Rebuild rollback must not publish a new watermark or half-populated schema. Existing readers may retain their WAL snapshots; existing writers must still receive `Stale` when their captured base no longer matches.

Current filesystem symlink checks occur before acquiring the advisory lock; this code does not establish immunity to arbitrary hostile pathname swaps by non-cooperating processes. Preserve and, where the admission refactor touches the path, revalidate the existing ownership assumptions rather than claiming a stronger filesystem identity guarantee. In-place logical recovery avoids introducing a new pathname-unlink race. A general hostile-filesystem redesign is outside this selected task unless the concrete witness exposes one.

## Actual frequency and cost gate

The workspace caches one search handle (`lib.rs:489–498`). Its worker caches `Open { reader, index }`; it calls `SearchIndex::open` lazily only while `open` is None (`search.rs:642–709`). The cache is cleared after a storage failure or missing index path. Ordinary queries, syncs and preparations on that worker therefore do not reopen or rescan. A new Workspace/worker/process does; a short-lived public CLI search usually pays admission once for that invocation. Thus “once per open” is **not** “once per installation,” and it can effectively be startup cost for every CLI search.

Four fixed command strings do **not** make work constant or hard-bounded. Bundled `sqlite3Fts5StorageIntegrity` scans/re-tokenizes external content to derive a checksum; four lanes mean Note and Message text are checked with their exact and stem analyzers. Existing `quick_check` already scans storage, but that does not prove the extra tokenization is cheap. The current busy timeout bounds waiting for a database lock, not CPU/I/O spent checking a large corpus. No existing progress/cancellation budget for this open scan was found. Do not describe the change as bounded-time merely because it is outside the query method.

**Before adopting automatic full verification, qualify admission cost.** Reuse the existing 10,000-Note scale witness: it measures cold build, reopen without rebuild, one-Note sync and query p95. Its strict release/target-Mac run also requires reopen under50 ms and at least4× faster than cold build; one-Note sync under50 ms and query p95 under150 ms. A lenient debug pass cannot establish those performance bounds. Record actual before/after admission/reopen timing, not only overall tests. That fixture has no substantial Message corpus, so separately measure the added Message-lane cost on a bounded synthetic Message-heavy existing fixture/adaptation before claiming all-four-lane scale qualification.

If the required startup/latency budget fails, **stop and reassess**, retaining the failing measurements. Do not waive the existing targets, add a scan per query, silently sample lanes and call the whole index healthy, or introduce a persistent “verified” stamp which arbitrary FTS-only changes can leave unchanged. An explicit diagnostic/repair route or a separately budgeted/background verification policy would be a different selected outcome and needs its own scope/acceptance decision. Always rebuilding at open costs more and violates fast reuse. Constant-time metadata alone cannot prove arbitrary content/index correspondence.
