## Call-path and counts

At `crates/brn-desktop/src/threads_ui.rs:805–902`, each `refresh()` does these synchronous state reads:

- `workspace.records()` at `:807`: `Workspace::records` delegates to `Store::records`, which selects and JSON-deserializes every `records.body` (`crates/brn-threads-app/src/lib.rs:280–282`; `crates/brn-threads-core/src/store.rs:624–628`).
- `workspace.history()` at `:808`: all receipt bodies are selected/deserialized (`lib.rs:323–325`; `store.rs:644–650`).
- `workspace.candidates()` at `:809`: all currently prepared, unreceipted operations are selected and expanded through `prepared_on` (`lib.rs:326–328`; `store.rs:652–656`).
- `recovery_buffers()` at `:810`: it selects every open edit-session ID then loads each session (`crates/brn-threads-core/src/edit.rs:62–67`).
- `workspace.settings()` at `:811`: this calls `self.records()` and scans that complete collection for the first non-archived Settings record (`crates/brn-threads-app/src/settings.rs:15–27`). This is a second full-record read in the same refresh.
- `workspace.topics()` at `:814`: it calls `self.settings()` again, making a third full-record read. If a Topics pointer exists, it then calls `Store::records_for_chat(None)`, which itself calls `Store::records()` and applies visibility/archive/supersession filtering to all rows (`crates/brn-threads-app/src/topics.rs:42–67`; `crates/brn-threads-core/src/context.rs:205,212–223`). With Topics configured, that is a fourth full-record read; without it, the fourth read is skipped.

The newly added ordinary 10k-note fixture reports its actual history/candidate/buffer/asset/Topics counts; it does not have a Topics pointer, so `topics()` stops after its Settings read. It therefore exercises three complete record loads during refresh, not the four-load configured-Topics branch.

There are conditional lookup costs beyond those bulk reads. `refresh_names` calls `writing_request` for each request message named by `history.needs_refresh` (`threads_ui.rs:817–833`). The `applied_rewrite` projection iterates history when any current writing-request Message exists, opens each eligible Note-apply operation using `store.prepared`, and may call `writing_request` for matching request inputs (`:834–871`). In a long history with at least one active request, this can add multiple per-receipt/per-input queries. The diagnostic fixture has no writing request or request-linked Apply, and prints that path as unactivated. `refresh_writing_review_cache` is called by `ThreadsUi::render` before constructing the UI body (`crates/brn-desktop/src/threads_shell.rs:1640–1652`), outside the direct `refresh()` timer. Its cache key includes the change token, open Note, writing scope, conversation, and shown candidates; an unchanged key returns without reloading (`threads_ui.rs:760–767`). A cache miss clears the prior batch and calls `Workspace::writing_context_review` (`:769–795`), which reads canonical records, receipts, and active candidates, then rechecks the change token before returning (`crates/brn-threads-app/src/review.rs:509–529,592–597`). Existing tests assert that unchanged renders reuse the checked batch and that ordinary typing does not reload it (`crates/brn-desktop/src/threads_writing_tests.rs:1028–1067`; `threads_workbench_tests.rs:1239–1271`). This render-time service work is excluded from the diagnostic interval around `view.refresh()`; any render/park work the update helper performs is also outside the timer. Thus the diagnostic is a direct refresh-method sample, not a complete render/startup cost sample.

## Smallest candidate and boundaries

One direct duplicate is avoidable without a cache or new public API: after `self.records` is populated, `refresh` can select the first non-archived `RecordData::Settings` from that already-loaded ordered collection instead of calling `workspace.settings()` for a second full scan. The local projection would need to preserve the existing first-match behavior and the same “Workspace configuration is missing” error. This repeats a small selector rule in the desktop crate; if that maintenance duplication is unacceptable, there is no existing `Workspace::settings_from(records)` service, and adding one would expand the app API. This is a candidate for later consideration, not an approved change.

The other repeated reads have no equivalent existing input-taking seam. `topics()` intentionally uses the core `records_for_chat(None)` visibility rules and its Settings pointer is not in that visible result set; `Store::records_for_chat` accepts no caller-provided snapshot. Avoid replacing it with a desktop-side hand-written visibility filter. Removing those repeated reads safely would need a shared snapshot/projection seam that can select Settings and compute the same scoped Topics result from one read. The current code has no such seam, so adding it without measured need would broaden API/responsibility. Likewise the per-receipt `prepared` lookups cannot be replaced with `candidates()`: candidates exclude applied operations, while the projection needs the request inputs of past applied receipts.

The refresh diagnostic reports total elapsed time and corpus/ancillary counts only; it does not attribute time by query or projection, and the detached `prepare_search` worker may still consume CPU concurrently. If the lead's single run identifies a material issue, the lowest-risk next step is a focused follow-up around reusing the already-loaded records for Settings selection, followed by a separate measured reassessment before designing a shared Topics snapshot. No broad cache, invalidation owner, public snapshot framework, data/version/provenance change, or Run/Undo behavior change is justified by this source-only audit.
