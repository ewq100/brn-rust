# Public backup interruption preflight

## Verdict: yes, it is a distinct useful boundary, but it is not yet authorized to run

A single bounded synthetic public-CLI backup interruption would add a user-facing process-boundary guarantee that the current core witness and public restore interruption do not establish. The current evidence already strongly supports the underlying core cleanup and retry behavior; the additional value is specifically to prove that the shipped CLI backup command, killed while its SQLite Online Backup is still producing a partial stage, leaves no final backup name and can remove that abandoned partial stage on one public backup retry.

## Existing evidence and limits

- The core process witness in `crates/brn-threads-core/src/backup.rs:450-544` launches the Rust test executable in its own child mode, waits until `StagedBackup::create` has returned, verifies `snapshot.sqlite3` is present and complete, then SIGKILLs the child. It proves actual SIGKILL/reap, complete unpublished staged snapshot retained, final name absent, released marker lock, public `Store::backup` retry removes the stage and publishes a valid backup, and source/sentinel preservation. It does **not** kill while Online Backup is in progress, and the killed process is the test executable calling the core API rather than the public CLI.
- Core source makes the shared behavior explicit: `backup.rs:74-88` creates the owned stage and runs SQLite Online Backup there; `:89-107` switches journal mode, validates and syncs the complete staged snapshot; `:110-125` exclusively hard-links the destination only in `publish`, then syncs its parent. Thus partial-work absence at the final path follows from the implementation structure, but the current child witness starts after this production stage operation completes.
- `/Users/evokessler/.codex/worktrees/vacation-hardening/brn-rust/docs/work/active/vacation-campaign/evidence/backup-process-bounds-qualification.json` records the completed core witness (219 passed, strict clippy and format/diff passed, with explicit qualification limits); the companion `backup-process-bounds-production-reuse.json` is source/config proof, not CLI runtime qualification.
- The public restore receipt at `/Users/evokessler/.codex/worktrees/vacation-hardening/brn-rust/docs/work/active/vacation-campaign/evidence/public-cli-restore-interruption-qualification.json` proves one actual public CLI restore killed with a retained *partial restore stage*, no final data directory, then public retry and exact logical/source checks. It is a different operation and does not exercise backup's stage or final `.sqlite3` publication behavior. Its source backup had been created with the public CLI, but that is a successful backup only.
- Ordinary public CLI backup coverage exists (for example `crates/brn/tests/agent_edits.rs:418-428`, and further CLI backup/restore journeys in `agent_edits.rs:609-640`, `agent_runs.rs:1338-1348`, and `agent_authority.rs:234-244`). These complete normal backup journeys; none of those inspected call sites kills a backup process during copying.

The reviewed restore driver is reusable as a bounded harness and fixture recipe, not as direct proof or a drop-in unchanged driver. Reusable pieces are fresh task-owned canonical roots, public CLI `init`/`note-create` fixture construction (including the deterministic 8 MiB Note), source pin/binary hash checks, secret-filtered environment, owned process wait/kill/reap, bounded stdout/stderr drains, read-only SQLite schema/row comparison, sentinel/source-byte preservation, one retry and cleanup, and durable result capture. Changed logic must launch `backup --destination`, observe the exact backup stage and `snapshot.sqlite3` growing to a nonzero size still below the complete source database, SIGKILL that owned CLI process, prove actual signal termination and the requested final backup path is absent while the partial stage remains, then retry the same public backup once and verify that stage was swept and the result is a valid standalone backup logically equal to the source. No production hook is indicated.
