## Why Cargo still has distinct work

- The helper is intentionally outside the main virtual workspace. It has its own standalone manifest and two committed lockfiles. The stock/adapted locks each contain 409 package records; 408 `(name, version, source)` identities are identical. The sole identity difference is `xberg 1.3.10`: registry source for stock, generated path source for adapted. Direct helper dependencies and Xberg feature selection (`pdf`, `office`, `excel`, `email`, `html`) are the same. The patches change Xberg source bytes, so compiling the adapted Xberg crate is a genuine second source build; stock and adapted executables and their exact-source checks are separate obligations.
- `build-document-helpers.sh` deliberately selects literal `target_root/stock` and `target_root/adapted` Cargo target directories and records each mode's expected source root. It rejects a target/source association mismatch. It also checks the adapted helper's generated engine identity, copies the built binaries into qualified artifacts, records the dependency graph, and hashes each artifact. Separate targets therefore prevent the two builds from sharing Cargo outputs even for registry dependencies whose lock identities and selected dependency features appear common. A common target directory could plausibly reuse many common registry units, but would cross the script's current source-root boundary and needs a design that retains its identity/refusal guarantees. Do not remove or bypass the guards based on this observation.
- The main workspace sets `profile.test.opt-level = 1` (and a package override for `sha2`), while the standalone helper manifest defines only `debug = 0` for its own dev/test profiles. Cargo reports helper test compilation as `test [unoptimized]`; root-workspace tests are `test [optimized]`. These are intentionally separate profile artifacts and helper tests do not inherit the root test profile.
- Per mode, preparation needs an executable dev-profile helper. The later `cargo test --all-targets` must build test harnesses and dependencies in the standalone test profile, then execute API/identity/restriction tests against that engine. `cargo clippy --all-targets` checks all helper and test targets with Clippy; the log shows broad `Checking` work in the dev profile. The dev executable, test-profile graph and Clippy check graph are different compiler obligations. The same mode's commands already point at the same target directory, so same-mode reuse is configured where Cargo's units match.
- The adapted workspace is intentionally regenerated under this checkout's ignored `target/xberg-adapted`; the generator pins its output location to that repository and refuses symlinks, mismatched patch/source hashes, modified occupied output, or a lock mismatch. It writes checkout-specific absolute manifest paths and preserves the accepted patch/source/engine receipt. CI explicitly removes the restored generated workspace and recreates it. This guards against trusting generated source from another checkout. Any cache/reuse change must keep those checks and regenerate/verify the current source before compiling or admitting a helper binary.

## Candidate ranking and limits

1. **Only plausible in-scope compile-reuse candidate; unqualified and not selected:** investigate whether common registry dependency units and the unchanged `brn-intake` path unit can be shared between stock/adapted while preserving exact generated-source, engine, binary hash and source-root admissions. The lockfiles make this technically plausible for common units; the distinct Xberg crate remains separate. The present literal target-root guard expressly forbids sharing one mode's target with the other, and no experiment here qualifies a safe design, estimates elapsed savings, or proves Cargo will reuse a useful fraction. Benefit: potentially avoid duplicated compilation of common units within one lane. Risks: contaminating or misattributing source-root artifacts, changing Cargo fingerprints/features/profile behavior, and weakening the fail-closed generated-path admission. Requires a design and dedicated evidence before any code dispatch.
2. **Keep all current helper build/test/lint commands and guarantees:** exact stock/adapted binary production, each engine's `--all-targets` functional/API/restriction/identity tests, and strict Clippy on each graph are all effective required work. Their bodies are cheap, but this does not make the assertions redundant. No command/gate/test removal is supported by this evidence.
3. **Do not infer Mac cross-lane artifact sharing here:** producer/consumer workflow topology, artifact transport/integrity, and required-check failure propagation belong to the separate CI lane/cache investigation and the existing deferred feasibility record.

No code or workflow fix is recommended from this bounded helper-graph audit. No cache-miss root cause is claimed.
