# Supplemental composer draft adoption audit

## Finding

Source-supported restart recovery defect in `adopt_writing_thread`: the draft transfer updates only `ComposerDrafts` in memory and never writes the new Thread key or clears the persisted Note key. A visible unsent draft can therefore disappear from recovery after restart, while its old Note-key row remains stale.

`open_note` initially chooses `ChatTarget::NewForNote(note)` when no writing conversation exists; changing that composer saves under `ComposerDestination::Note(note, None)` through the editor Change subscription ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L515), [threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1166)). `post_comment` and `rewrite_note` both call `ensure_writing_thread` and then `adopt_writing_thread` ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1610), [threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1690)). `ensure_writing_context` creates and links a real writing conversation if none exists ([writing.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-threads-app/src/writing.rs#L205), [writing.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-threads-app/src/writing.rs#L221)). The first branch of `adopt_writing_thread` then changes `self.chat` directly and calls only `composer_drafts.posted(&pending)`; it does not call `save_composer` for either destination ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1051)). There is no editor value change in that branch, so the normal Change subscription cannot persist the Thread key.

On startup, `ThreadsUi::new` reads the persisted draft rows into the in-memory map ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L436)). Reopening the Note now resolves its newly created writing conversation and selects `ChatTarget::Thread(thread)`; `set_chat` loads that Thread key ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1148), [threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1036)). Since the Note-key row was never copied and the Thread key is absent, the visible draft is lost on this recovery path. The stale Note-key row remains in `chat_drafts` but is no longer the destination selected by the persisted writing context.

The second branch has the same persistence gap: it moves a Note draft to the Thread key only with `posted`/`preserve` in memory ([threads_ui.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_ui.rs#L1061)). It may later get persisted when that Thread is selected and an editor Change occurs, but a restart before that leaves it only at the old key.

## Existing coverage and next evidence

The `submit_note_edit` route explicitly persists the Thread draft and checks it before posting, then clears the Note draft ([threads_context_actions.rs](https://github.com/ewq100/brn-rust/blob/bc8a08e64b0dc1e2b33ff181dfdb54b62f59f5e4/crates/brn-desktop/src/threads_context_actions.rs#L163)); this demonstrates that the handoff needs a durable write. Existing tests cover that route's refusal/retry, and a context-action test checks the note draft transfer. I found no existing test of `adopt_writing_thread` with a nonempty `NewForNote` draft, and no composer adoption restart/recreation witness.

A small deterministic view-recreation test is needed to turn the source-supported finding into an exercised regression: save a Note-context composer draft, trigger first comment or rewrite to create/adopt its writing chat, recreate `ThreadsUi` on the same disposable Workspace, reopen the Note, and assert that the Thread composer still shows the exact draft and that the old Note destination is cleared or otherwise intentionally retained. No test/build was run per the bounded read-only assignment; no repository files were changed.
