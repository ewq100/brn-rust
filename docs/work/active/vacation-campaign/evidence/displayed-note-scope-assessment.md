## Scope result

For ordinary Note open and reload, the host’s writing/setup/review scope is coherent with the displayed `NoteLifecycle` identity. `open_note_in_context` resolves an `ActiveWritingContext` before loading (`crates/brn-desktop/src/threads_ui.rs:1192-1207`), and only after `WritingPanel::open_note` succeeds does it assign both `note_writing_scope` and the Project-only `note_project` projection (`1222-1237`). The lifecycle loads/validates the canonical Note and recovery buffer before replacing its `OpenNote` state (`crates/brn-writing-ui/src/note.rs:77-160`); a refused load keeps the prior open Note and the host returns before changing either scope field. `open_project_note` and `open_thread` pass their actual Project/Thread origin through this same path (`crates/brn-desktop/src/threads_projects.rs:93-110`; `threads_ui.rs:1271-1282`). Explicit writing-chat selection re-resolves the selected conversation and then updates the scope and thread mapping together (`threads_ui.rs:1604-1637`). The core resolver derives Project identity for Project chats, private-chat identity for private Threads, and general scope otherwise (`crates/brn-threads-core/src/writing.rs:111-126`; `crates/brn-threads-app/src/writing.rs:138-236`).

`note_project` is deliberately narrower than `note_writing_scope`: it is set only when the resolved scope ID is a Project record, and its sole consumer is the Connections request (`threads_connections.rs:90-100`). Writing review cache, setup load/save/validation, rewrite and reference-import checks use the displayed Note plus `note_writing_scope`; the review cache key binds both Note ID and scope and clears on checked-context failure (`threads_ui.rs:742-803`, `3903-4018`, `4243-4355`). `refresh_note` is used after an applied Note rewrite; it reloads the same checked Note and buffer without changing its chat/protection identity, so the host scope does not need to be inferred from a new mutable global chat (`threads_ui.rs:2490-2499`; `brn-writing-ui/src/note.rs:248-300`).

## One distinct delayed-consumer gap

There is a supported ordering where a previously valid project-scoped Connections result can remain visible after its Project document link is revoked. Open a private imported Note through a Project that has linked it, show Connections and let the request populate, then use the same Project document row’s `Unlink` action (`crates/brn-desktop/src/threads_projects.rs:440-487`). `apply_project` commits the unlink and refreshes canonical records but does not invalidate or reload Connections (`threads_projects.rs:112-148`). `refresh_connections` is the operation that increments the graph generation, cancels the outstanding request and clears the current result (`threads_connections.rs:61-103`); the async completion is accepted whenever that generation remains equal (`109-125`). Rendering keeps a result whose centre still has the displayed Note ID (`threads_connections.rs:207-220`) and does not recheck its neighbours against current scope. Thus an already completed result, or a pending pre-unlink request, can still present source/Note labels that were visible because of the now-removed Project link. Core visibility is correctly link-based (`crates/brn-threads-core/src/context.rs:20-41, 43-54`); the gap is retaining the old host view, not a missing store permission check. The existing connection test covers depth-change invalidation, not Project-link revocation (`crates/brn-desktop/src/threads_tiled_tests.rs:1100-1195`).

This does not make the writing/setup/review scope fields themselves diverge: they continue to represent the Project origin selected when opening the Note, and their checked consumers fail closed if that context is no longer available. It is a separate `note_project` delayed-view freshness gap. Smallest follow-up: have successful project membership changes invalidate/re-request Connections for the currently displayed Note, retaining the existing generation/cancellation mechanism and existing visibility predicate; do not reinterpret the selected writing scope or auto-switch the Note to general.
