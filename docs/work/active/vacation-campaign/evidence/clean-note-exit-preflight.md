# Clean stale Note during normal exit — read-only preflight

**Source:** `/Users/evokessler/.codex/worktrees/mac-test-roots/brn-rust`, branch `codex/note-exit-preservation-20261022`, clean HEAD `660a737174030320ca4c412248117a168e69c8d6` before and after inspection.

**Finding: concrete valid-input false exit refusal.** A clean editor can retain a previously saved vN body after another checked `Workspace` commits vN+1. Ordinary desktop `ThreadsUi::refresh` reloads `self.records` and other app collections (`crates/brn-desktop/src/threads_ui.rs:805-814`) but does not call `WritingPanel::refresh_note` or replace the open lifecycle record. The explicit checked-change path `reload_open_note` does call `refresh_note` (`threads_ui.rs:2490-2499`), but an independent Workspace/CLI write has no callback into this window. Therefore the supported sequence “open clean Note at vN; another Workspace begin-edit/update-buffer/save at vN+1; app refresh; normal Close” leaves the first window with the old body and `EditState::Clean`.

On Close, `preserve_note_for_exit` checks current `Store::note(id)` and open recovery buffers only (`crates/brn-writing-ui/src/note.rs:88-121`). The current Note body is vN+1 and there is no open recovery buffer, so its check is false. It then calls `note_changed` with the visible vN text. `note_changed` compares against the lifecycle's cached `open.record` and returns `Ok(None)` for a Clean editor whose text equals that cached body (`note.rs:232-245`), without starting an edit. The second durability check remains false and the guard returns the refusal error (`note.rs:100-108`). `ThreadsUi::request_exit` translates that into the “Could not keep the latest note text” notice and explicit discard dialog (`threads_ui.rs:4909-4923`). No canonical data is lost, but a clean, already-saved view is treated as unpreserved local typing and Close is unnecessarily refused.

The old body is independently provable as durable: `Store::revision(id, version)` reads the immutable `(id, version)` record from `revisions` (`crates/brn-threads-core/src/store.rs:632-642`), and `read_note_revision` explicitly supports historical revisions after later edits (`crates/brn-threads-core/src/revision_read.rs:51-70`). This is not a hypothetical dirty-session race; it is the ordinary clean case with a concurrent successful version advance. Current exit coverage tests an unsaved typed edit, a kept recovery buffer, a closed cached session whose body is now canonical, and a newer open recovery buffer (`crates/brn-desktop/src/threads_writing_tests.rs:1782-1815, 2013-2150`); it does not cover a clean stale cached body that matches an immutable prior revision.

The current behavior contract says Close first ensures visible bytes are canonical or in open recovery, and that a “newer local session” does not prevent exit if those bytes are durable (`docs/architecture/threads-behavior.md:106`). The writing UI README repeats the canonical/open-recovery alternatives (`crates/brn-writing-ui/README.md:13`). Neither explicitly classifies a clean held historical revision. The existing revision API supplies a narrow proof without inventing a new persistence mechanism.

**Smallest follow-up evidence:** extend the existing Close-preservation journey with a clean Note opened at vN, a second checked Workspace Save to vN+1, then Close from the first window while its lifecycle remains clean and visibly at vN. Assert the immutable `revision(id, vN)` body matches the editor, the current vN+1 Note/history remain unchanged, and normal Close is admitted without creating an edit/recovery buffer. The focused policy decision is whether an exact immutable historical revision counts as preserved for this clean-editor case; no source change or test was made here.

No test, build, CLI, SQL fault or native interaction was run. This identifies a state-level Close predicate consequence; it does not claim native-window closure behavior.
