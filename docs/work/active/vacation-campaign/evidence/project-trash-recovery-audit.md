## Binding and checked write path

- The Projects menu derives its target from the currently shown, active project and captures that ID (`crates/brn-desktop/src/threads_projects.rs:150-170`). Opening deletion computes a preview for that ID and derives the displayed project title (`:924-946`). The dialog shows the titles moved/kept, describes hidden dependent item kinds, requires explicit choices for unfinished Actions, disables confirmation while choices are incomplete, and keeps Enter inert (`:956-1022`). Its confirm closure retains the preview and submits a clone of that exact preview (`:1011-1042`). On service failure it leaves the dialog open and says nothing moved; it instructs the owner to reopen the action to refresh the list (`:1038-1042`).
- The preview is derived from a current active Project (`crates/brn-threads-core/src/projects.rs:184-188,206-305`). Its removal set includes the project and relevant chats, exclusive notes, dependent Messages/Runs/Assets/Comments/Links and eligible Actions; shared notes are retained (`:211-289`). The snapshot serializes removed, retained and unfinished-Action records, including their IDs, versions and data (`:290-304`). At delete, core recomputes the preview inside an immediate SQLite transaction and requires exact equality before checking that every unfinished Action has one choice (`:331-359,547-565`). Stale membership, changed records or changed project versions therefore reject before writes.
- Dirty notes are covered at the shared checked writer: applying a write finds any open edit session on each target and returns `Deferred` for guarded targets (`crates/brn-threads-core/src/store.rs:1952-1973,2322-2327`). Project commands treat a non-applied outcome as an error and commit only on success (`crates/brn-threads-core/src/projects.rs:809-832`). The existing app test opens an edit session on an exclusive Note, attempts deletion, and asserts the Project remains active (`crates/brn-threads-app/tests/projects.rs:254-266`).
- Archiving a protected Note requires the checked `Archive` capability when its archived flag changes (`crates/brn-threads-core/src/store.rs:2169-2187`). The shared Project service executes with `HostAuthority::owner` (`crates/brn-threads-app/src/projects.rs:11-23`); Owner scope is allowed by the capability check (`crates/brn-threads-core/src/types.rs:655-657`), and core rejects non-owner Project commands (`crates/brn-threads-core/src/projects.rs:331-342`). The user-visible preview names moved Notes; the explicit owner-confirmed operation is Trash/recoverable rather than permanent erasure. There is no direct test of a protected Note traversing this specific Trash route; the authority and archive requirement are source-backed, not runtime-qualified here.

## Restoration, later work, and identity

- Delete records each child’s exact post-delete version and its prior archived state (`crates/brn-threads-core/src/projects.rs:572-598`). Restore’s UI captures the selected trashed Project’s ID and version when that view is built, then sends both (`crates/brn-desktop/src/threads_projects.rs:341-345,356-384`). Core finds that same archived Project ID/type and refuses a mismatched Project version (`crates/brn-threads-core/src/projects.rs:632-645`). It then checks every trashed child by ID, exact `deleted_version`, and archived state before restoring any; a conflict returns “preserved in Trash” (`:649-675`). Eligible children regain their original archived state, so pre-archived records are not accidentally made active.
- The stale-preview witness posts a new message after preview and confirms deletion is refused (`crates/brn-threads-app/tests/projects.rs:364-389`). It then edits a trashed exclusive Note and confirms Restore is refused while Project and chat stay archived (`:390-422`). The test does not explicitly assert the later Note bytes or Trash metadata after refusal; the source returns before preparing writes for that conflict, and the transaction commits only at the end of the successful path (`crates/brn-threads-core/src/projects.rs:649-663,809-832`).
- A complementary service witness edits a shared Note after the other Project was trashed, reopens the workspace, restores, and checks the later shared content remains exactly `Later adopted shared writing` (`crates/brn-threads-app/tests/projects.rs:300-359`). It also checks exclusive-note/comment recovery and explicit Cancel/Keep Action outcomes (`:287-358`). The native UI witness checks a shared document remains active, the Project link returns, and the unsent draft remains (`crates/brn-desktop/src/threads_projects_tests.rs:113-141`); this is test-source evidence, not a native observation from this audit.
- Project deletion fences affected working Runs and pauses queued work, clearing pending dispatch (`crates/brn-threads-core/src/projects.rs:717-759`). Restore does not clear that pause or restart a Run; the Trash view tells the owner work stays paused (`crates/brn-desktop/src/threads_projects.rs:23,356-384`).

The current contracts match those checks: protected-note archive needs owner authority (`docs/architecture/threads-target.md:126-135`); dirty groups defer and stale/Trash conflicts preserve recoverable state (`docs/architecture/invariants.md:44-46`); and Trash restore does not reverse cancelled/outside Actions or restart work (`docs/architecture/threads-behavior.md:84`). The campaign workflow currently labels this full Project path **UNQUALIFIED** (`docs/work/active/vacation-campaign/workflows.md:41`), so this source audit does not upgrade UI/native status or owner acceptance.
