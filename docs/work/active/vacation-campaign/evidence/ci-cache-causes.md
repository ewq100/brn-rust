# Mac CI cache cause and reuse assessment

Observed at repository `d18a644b0709f2312adc3e89c5266d5f9fcb0c86` on branch `codex/agent-first-followthrough`; repository working changes were only the lead-owned campaign/overview files and were left untouched. This is a read-only source/log assessment; no workflow, cache, Git, account, or test state was changed. v3 adds the earlier main run that had restored the same key and later found it unavailable.

## Findings

Correction in v2: the pinned action does not hash every Cargo lockfile and manifest found anywhere in the checkout as the README summary suggests. Its implementation uses configured workspace metadata and each configured workspace root lockfile. Here the only configured workspace is the repository root.

1. **A previously available main cache became unavailable; this was not the first population of this key.** `.github/actions/setup-rust/action.yml:46-53` pins Swatinem/rust-cache `6323deb102c322ba6fcbdcafc7e3dddab59af2b6` and composes the key from OS, architecture, lane, root `Cargo.toml`, plus the action's Rust/compiler/environment/lockfile suffixes. Earlier main run39392850688 Mac Core restored the exact final key at 08:22:38Z with a full match and 993,860,160 bytes (`/tmp/brn-main02445-mac-core.log:267-285`), then reported `Cache up-to-date` at 08:46:50Z (`:3673-3676`). Main20f Mac Core later reported `No cache found` for that same final key at 09:29:54Z (`/tmp/brn-main20f-mac-core-cancelled.log:240-267`), and PR182 reported `No cache found` at 09:46:22Z (`/tmp/brn-pr182-mac-core.log:247-263`). Main20f then saved a new 993,892,067-byte archive at 10:14:37Z (`docs/work/active/vacation-campaign/evidence/ci-main20f-timeout.json:221-225`); the 10:59:57Z retry restored it as a full match (`/tmp/brn-main20f-mac-core-retry.log:273-276`). The exact key string is unchanged across the earlier hit, later miss and replacement. The earlier and later workflows used the same cache paths (`.cargo/registry`, `.cargo/git`, checkout `target`; `/tmp/brn-main02445-mac-core.log:234-243`, `/tmp/brn-main20f-mac-core-cancelled.log:234-243`), and a Git diff confirms `.github/actions/setup-rust/action.yml` and `.github/workflows/ci.yml` were unchanged from `02445b283d85ac09d24f7ee7f111039a87b4dbb5` to `20fcd7383662cd2f67607c3ce04194aed50809b5`. The evidence supports an exact-key cache becoming unavailable between 08:46 and 09:29; it does not identify eviction, expiration, manual deletion, backend/service behavior, or another cause. Ref scope still explains why PR archives are distinct from main, but it cannot explain the earlier main-ref hit followed by a main-ref miss.

2. **Ref scope creates separate PR and main archives.** The supplied inventory `/tmp/brn-ci-cache-inventory.json` has six entries totaling 8,936,986,355 bytes (about 8.94 GB): PR182 refs account for 5,886,330,190 bytes (about 5.89 GB), and main refs for 3,050,656,165 bytes (about 3.05 GB). For Mac default, the main and PR182 entries share the same key and version (`e857…2296`) but have distinct IDs; the native Mac lane has the same duplication. This reflects ref-scoped cache writes. GitHub documents that PR runs may restore base/default-branch caches, while caches created under `refs/pull/.../merge` are limited to reruns of that PR and cannot be restored by main or sibling PRs ([GitHub cache scope documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). The 09:46 PR miss occurred after the earlier main archive had become unavailable and before main20f saved its replacement; the current snapshot then records separate main/PR copies. These counts show a substantial PR share of the current snapshot, not historical storage pressure or a proven eviction cause.

3. **A full hit does not retain the converter helper build products.** The pinned action caches Cargo registry/git and the root `target` by default (`/tmp/brn-rust-cache-pinned/src/config.ts:265-281`; README says cached target artifacts are dependencies, `/tmp/brn-rust-cache-pinned/README.md:137-171`). Before saving, it runs full `cargo metadata --all-features` from the configured root, then filters to dependency packages whose manifests are outside the root (`src/workspace.ts:18-32,40-42`; `src/save.ts:39-50`). It prunes target profile outputs to that set (`src/cleanup.ts:39-79`). CI builds the stock helper using `tools/xberg-intake-helper/Cargo.toml` and adapted helper using generated `target/xberg-adapted/workspace/Cargo.toml`, with separate custom targets below `target/document-helpers/{stock,adapted}` (`.github/workflows/ci.yml:79-109`). Those helper packages live under the repository root, so the root cache's outside-root dependency set excludes the helper binaries themselves and any dependencies used only by the standalone helper graphs. The recursive cleanup enters nested profile directories under `target/document-helpers`; common third-party dependencies that also occur in the default root graph may survive there. The action therefore cannot preserve the helper executables and may prune helper-only graph artifacts, even though the paths are inside the cached root target. The helper `Cargo.toml` files and standalone helper lockfiles are absent from both the printed “Lockfiles considered” list and the pinned implementation’s key inputs. The README generalizes that all manifests/locks “found anywhere” are hashed, but `src/config.ts:154-248` does not do a checkout-wide manifest/lock glob: it gets manifests from `getWorkspaceMembers()` of configured workspaces and hashes each configured workspace root `Cargo.lock`. This is an implementation/documentation mismatch. The root workspace dependency set also means helper-only graph outputs are not kept by target pruning, and helper-only registry archives may be removed when the root graph is cleaned. These are pinned-action scope effects, independent of ref misses.

   The recovered main log reports many dependency and helper `Compiling` lines; stock and adapted helper builds finish at 11:02:09Z and 11:04:08Z (`/tmp/brn-main20f-mac-core-retry.log:615-686`). The cold run's helper step ran 09:30:11-09:45:10Z. The lead-provided job receipt reports same-source cold elapsed time of 2,708 seconds and exact-key warm retry elapsed time of 886 seconds; the warm Mac Core job passed. This is one useful same-source cold/warm observation, not a stable benchmark across runner variation. The helper compilation was still not skipped.

4. **`target/xberg-adapted` is deliberately removed after restore.** `.github/actions/setup-rust/action.yml:54-59` deletes it because it contains checkout-specific generated paths. That directory is source/workspace generation, not a reusable compiled artifact. Do not preserve it as a cache workaround. Recreate it each run as current workflow does.

## Candidate risks and evidence needed

Under this 8.94 GB snapshot, the narrowest write-side mitigation to evaluate is forwarding Swatinem/rust-cache `save-if` as true only on pushes to `refs/heads/main`. The pinned action supports `save-if` and defines false as restore-only (`/tmp/brn-rust-cache-pinned/action.yml:47-50`; `src/save.ts:16-28`). This could stop future PR-scoped duplicate uploads while preserving PR restore from main when a matching cache is available. Its cost is that a PR with a new dependency/lock key cannot seed its own next run: those reruns remain cold until the matching main run saves the key. Existing required checks would still execute. This is the safest small follow-up to assess if storage churn is the goal; it has not been implemented or qualified. The current main/PR split is 3.05/5.89 GB; changing save eligibility would not remove existing PR caches. The current snapshot alone does not prove storage quota pressure, and it does not explain why the earlier exact-key main archive became unavailable.

The standalone helper lockfiles are a separate potential cache invalidation/reuse gap. The Mac logs’ “Lockfiles considered” blocks show the root `Cargo.lock` and root workspace member manifests only (`/tmp/brn-main20f-mac-core-retry.log:252-264`; PR log `/tmp/brn-pr182-mac-core.log:247-259`). The stock helper has its own `tools/xberg-intake-helper/Cargo.lock`; a read-only `tomllib` comparison found 136 `(name, version)` tuples in that lock absent from the root lock, representing 82 names not present in the root lock at any version. These are missing lock inputs, not a count of artifacts pruned: the pinned target cleaner keeps files by package/target name (`src/cleanup.ts:65-79`), so some helper versions whose package name is present in root dependencies may remain in the archive. The adapted workspace is generated from source during the job and likewise has a standalone generated lockfile. Because neither helper workspace is configured as a rust-cache workspace, its lock is not an automatic key input, and helper-only package names are outside the root dependency keep-set. A helper dependency/lock update can therefore leave the cache key unchanged while relevant helper artifacts/registry entries are omitted from the next archive. Cargo still resolves the explicit locked helper graph in the job, so this is a cache freshness/reuse risk, not evidence of an incorrect build result.

If helper caching is later selected, bind the helper lock inputs into the cache key and measure the narrow helper-only artifact set before retaining it. Broad raw helper target directories can accumulate build outputs and receipts and add substantial archive size; do not adopt them casually. Preserve all existing OS/architecture/lane/Rust/root-lock scopes and required checks, and leave generated `target/xberg-adapted` ephemeral. Any helper-cache change remains an unqualified candidate.

The earlier exact-key main hit followed by a later miss proves a cache availability transition, not its mechanism. Neither inventory snapshot nor job logs establish deletion, eviction, expiry, quota pressure, or an admin/backend action. The inventory is a point-in-time sample, not an audit trail. The helper cleanup source and repeated helper compile output support the pruning mechanism; the same-source cold/warm job timing (2,708 seconds versus 886 seconds) shows the warm retry completed sooner, but a single pair cannot isolate cache savings from runner variation.
