# Note storage-refusal preflight

**No source-backed loss, guard-discard, or false-Save path found.** This is a source assessment, not an injected-I/O qualification. Product source is integrated `origin/main` `10f2ff80a39408ce411e10c77200e6d4a89b12d3`. The concurrent working branch is docs-only through `736f40bad4ccd1eb37b1c9212ed3004aea1f1bf9`; the inspected Note lifecycle, core edit and relevant test files match `origin/main` and are unchanged in the working tree. I made no workspace changes.

Typing reaches `ThreadsUi::note_changed` on each editor Change (`crates/brn-desktop/src/threads_ui.rs:555–566`). The lifecycle creates a durable session at first dirty input, then commits each new generation in a separate immediate SQLite transaction (`crates/brn-writing-ui/src/note.rs:162–223`; `crates/brn-threads-core/src/edit.rs:8–16,72–94`). It updates the in-memory session only after `update_buffer` returns `Updated`. Therefore, if begin/update/commit returns a storage error, the UI text remains in the editor and the old in-memory/durable session is not replaced by the failed generation. The desktop surfaces “Could not preserve this edit … Keep this window open or copy your text” (`threads_ui.rs:1398–1417`). A failure before the first successful `begin_edit` has no durable guard yet; a failed later buffer update leaves the previously committed buffer/guard, not the newer typed bytes. If the process exits before retry, the latest uncommitted-to-SQLite characters cannot be recovered. This is the unavoidable limit of a refused durable write, and the UI explicitly warns about it; no silent discard in the live view was found.

Explicit Save first calls `note_changed` with the exact visible editor value and stops on error; only then does it call `Store::save`. Save changes the Note and closes/clears the edit buffer in the same immediate transaction, and returns `Saved` only after commit (`note.rs:248–266`; `edit.rs:139–148,279–365`). Any transaction error propagates; desktop displays it as an error, not a success notice (`threads_ui.rs:1420–1436`). Non-error rejections such as stale generation/base return a `SaveOutcome` and retain the session/text; only `Saved` reloads the Note. `open_note`/`refresh_note` also propagate a failed attempt to preserve current editor text before replacing/reloading it (`note.rs:81–107,286–300`).

Existing witnesses cover adjacent, distinct behavior but not SQLite I/O refusal: `threads_document_tests.rs::stale_save_and_comment_keeps_typed_source_and_comment_draft` and `::late_checked_refresh_preserves_newer_typed_buffer_and_stale_save` exercise stale canonical versions and exact retained buffers; core `tests/core.rs` covers stale Save and edit-session/generation guards. They do not simulate `SQLITE_BUSY`, `SQLITE_FULL`, or read-only write failure. No false-success path appears in the checked code, so that gap alone does not establish a product defect.

If a future bounded failure witness is selected, the least invasive deterministic method is a core-only synthetic Store test: hold `BEGIN IMMEDIATE` on a second connection to that fresh database, then invoke `update_buffer` or `save` on the Store connection. The configured busy timeout is five seconds (`store.rs:154–156`), bounding the wait; assert the prior generation/session and canonical Note remain unchanged and the operation returns an error. This would prove transaction refusal/rollback, not desktop toolkit rendering, filesystem-full behavior, power-loss durability, or native acceptance; no such test or SQL was run here.
