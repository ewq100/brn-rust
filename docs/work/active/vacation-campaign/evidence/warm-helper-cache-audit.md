## Finding

A small experiment using the already pinned `Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6` multi-workspace inputs is feasible. It can cache the two existing helper target directories independently and ask the action to prune each against the stock helper's dependency graph. The adapted workspace need not exist during restore-time metadata collection: `tools/xberg-intake-helper/adapted.Cargo.lock` differs from `Cargo.lock` only in the `xberg 1.3.10` package's `source` and `checksum` lines. The pinned action hashes Cargo.lock package records while excluding `source`/`checksum` for local packages, which is the relevant normalization for generated adapted Xberg. The locks therefore encode the same dependency package graph as currently committed.

Proposed configuration shape, for a follow-up implementation/review (not applied here): retain the root workspace entry and add two workspace-target entries rooted at `tools/xberg-intake-helper`, mapping to `../../target/document-helpers/stock` and `../../target/document-helpers/adapted` (the action resolves each target relative to its workspace root). This gives restore/save metadata a maintained, present workspace and gives the cleaner the stock helper's external dependency set for both disjoint targets. Add an explicit cache `key` digest covering the adapted lock, helper manifest/build script, `scripts/prepare-xberg-adapted.py`, and the accepted Xberg archive/patch/source-manifest identity inputs. Preserve existing OS, architecture, lane, Rust toolchain/host, root profile, normal manifest/lock hashes, separate target paths, and main-only `save-if`. The action's existing `workspaces` inputs automatically hash the stock helper manifest and stock lock; explicit `key` input is needed for the adapted lock and patch/engine derivation because its generated manifest is absent at restore time.

The cache paths would be the helper's `stock` and `adapted` target directories only. The current workflow places generated source and its `source-manifest.json` under `target/xberg-adapted`; helper artifacts and receipts are siblings under `target/document-helpers/artifacts` and `/receipts`; source-root guard files are siblings named `stock-root.txt` and `adapted-root.txt`. None are inside the proposed helper target directories. The existing post-restore `rm -rf target/xberg-adapted` remains in place, followed by preparation and exact stock/adapted builds. No target is shared between engines. Existing source/engine build guards and every check remain intact.

This is a configuration experiment, not a guaranteed speedup. It depends on confirming the action's cleaned archive contains the dependency artifacts needed for helper builds while excluding helper binaries and all sibling source/receipt/guard paths. Keep the first run on PR read-only restore semantics and allow only main to publish. Inspect its exact cache key, restored files, save size, and helper-preparation times before considering continuation. Do not use `cache-directories` to capture a whole target subtree: that bypasses the workspace dependency pruning route.

## Follow-up disposition: overlap makes the proposed mapping unsafe

The earlier proposed duplicate-root mapping is **not safe as written**. It maps both helper target directories beneath the root workspace target (`target/document-helpers/...`) while the root workspace cache path remains the entire `target` directory. In the pinned action, `config.ts` adds each configured workspace target as a cache path (`src/config.ts:274-277`), so the root entry includes all descendants. On save, `save.ts:39-50` iterates workspaces in configuration order; the root workspace comes first and calls `cleanTargetDir(rootTarget, rootPackages)`. `cleanup.ts:10-36` recursively descends every directory. It recognizes nested `debug` profile directories by `build`, `.fingerprint`, or `deps` (`:18-30`) and `cleanProfileTarget` retains only names from the supplied package set (`:62-79`). Thus the root pass prunes helper `debug/deps` against the root graph before the subsequent helper entries can clean their own targets. The later helper passes cannot restore removed dependency outputs. This is the concrete failure mode; helper-only compilation can remain cold despite an exact cache hit.

The cache path is broad too: `target` is itself a cache path, and adding more workspace paths does not subtract descendants (`config.ts:274-281`). The pinned save cleaner does, however, recursively remove ordinary files in non-profile subdirectories (`cleanup.ts:13-37`): helper artifacts, receipts, root guard text, and generated adapted source under `target` are removed before upload in the normal successful save path. They are therefore inside the path being processed, but the current cleaner is intended to remove them before the archive is written. This is not an explicit path exclusion, and it relies on cleanup completing; exceptions during recursive cleanup are swallowed at `cleanup.ts:26-32` and at the caller (`save.ts:49-52`). Treat the action's cleanup as an observed pruning mechanism, not a structural guarantee that the cache path excludes those files.

Smallest distinct-target layout to test: keep the root workspace's existing cache target at `target`, but move the helper build target root to a sibling of `target` (for example, a job-local `../brn-document-helpers` directory adjacent to `GITHUB_WORKSPACE/target`). Configure the two helper workspace entries with relative target paths escaping from `tools/xberg-intake-helper` to that sibling's `stock` and `adapted` directories. The action resolves each configured target with `path.join(root, target)` (`src/config.ts:144-150`), so an appropriate relative `..` path can point outside the root `target`. Pass the same sibling directory to `build-document-helpers.sh --target-root`; leave its per-engine subdirectories, root markers, artifacts, and receipts there. Now root cleaning cannot descend into helper outputs, and the later helper entries prune their respective target dirs using the stock helper graph. Verify the runner-relative path normalization and actual resolved paths before use; this audit did not execute Node or a CI workflow.

The generated adapted source remains at the required `target/xberg-adapted` location and inside the root cache path. The root cleaner recursively removes its ordinary files before a successful save, and setup still deletes/regenerates it after restore. If structural exclusion of that generated-source subtree is required independent of the action cleaner, the root workspace target itself must be moved to a narrower dedicated target directory (with `CARGO_TARGET_DIR` and workflow binary paths aligned), which is a larger workflow change. Do not claim the previous duplicate-root configuration safely caches only helper outputs.

The distinct-target proposal remains only an experiment. Preserve both helper locks and their relationship, root/profile/OS/architecture/toolchain dimensions, patches and engine identity in the key; maintain main-only saves, independent engine targets, source-root guards, regeneration, and all checks.
