# Invalid backup error audit

**Scope:** Read-only inspection of `codex/agent-first-followthrough` at `10fd90595d6aacfc79b552450e6fc14d5c339962`; no source edits or builds. The requested observed binary is bound in the supplied campaign evidence to product crates at integrated commit `6622443e`, so source-level mapping below is from this worktree's stated HEAD, while the concrete CLI observation is the archived run.

## Finding

This is an actionable error-clarity gap for the specific observed malformed-file case, not evidence that restore safety failed. The evidence records exit 1, `internal` / `storage_error`, message `SQLite: file is not a database`, and verifies no final destination/stage publication and unchanged source bytes (`docs/work/active/vacation-campaign/evidence/mac-backup-cli-invalid-input.json`, JSON fields `exit_code`, `stdout`, `result`, `limits`). It characterizes this as fail-closed, but does not explicitly declare the `internal` classification intentional.

The documented taxonomy says `storage_error` is an unexpected SQLite or record-encoding failure (`crates/brn/README.md:181`), while `unsafe_directory` includes foreign/newer formats and missing databases (`crates/brn/README.md:165`). A literal non-SQLite file is caller-supplied invalid backup input and currently leaks a low-level SQLite diagnostic under the general unexpected-storage bucket. That is inconsistent with the nearby foreign/missing-format treatment and less actionable than the CLI's stated model of rejection for safeguards/current-state refusal (`crates/brn/README.md:115`).

## Trace and boundaries

- `Store::restore` enters staged restore (`crates/brn-threads-core/src/restore.rs:13-18`). `StagedRestore::create` opens the source read-only before preparing the target (`restore.rs:33-41`). Thus this malformed-file error occurs before any target parents or restore stage are created.
- `validate_schema` reads SQLite application/schema identity. A valid SQLite file with a foreign or unsupported identity becomes `Error::UnsafeDirectory`; a `quick_check` integrity result other than `ok` becomes `Error::Invalid` (`crates/brn-threads-core/src/store.rs:1467-1478`). A non-SQLite byte file fails while the source is being validated before staging and remains `Error::Sqlite` (`restore.rs:33-39`; error display prefix at `crates/brn-threads-core/src/lib.rs:48-59`).
- CLI restore directly calls `Store::restore` (`crates/brn/src/main.rs:983-987`). Conversion maps all SQLite errors except lock contention to `Code::StorageError` (`crates/brn/src/contract.rs:574-580`), and `StorageError` maps to `internal` (`contract.rs:250-253`). So the observed result follows the generic mapper; there is no restore-specific classification.
- The native app API has `AppError::Core` as a transparent wrapper for core errors (`crates/brn-threads-app/src/lib.rs:59-75`) and exposes backup (`lib.rs:583-588`), but repository search finds no app/desktop database-backup restore entry point or native restore error presentation. Therefore there is no native restore mapping to compare. Core `Store::restore` returns typed `Error` to any future native caller; current evidence's `limits` also correctly says it is not native wording evidence.
- Existing core coverage intentionally checks corrupt bytes, unsupported schema, foreign database, and empty source uniformly for error, no target-parent creation, and unchanged source (`crates/brn-threads-core/src/restore.rs:421-444`), but does not assert a user-facing category. Existing CLI contract coverage asserts occupied target as `unsafe_directory` (`crates/brn/tests/agent_contract.rs:1251-1255`), not malformed source. No found test or contract text explicitly blesses malformed bytes as `internal`.

## Recommendation and limit

Treat the exact observed `SQLITE_NOTADB`/"file is not a database" source-validation failure as an invalid/unsafe backup refusal with concise restore-specific guidance, preserving the existing no-publication behavior. Keep other SQLite failures, filesystem I/O, and ambiguous corruption/integrity failures on their existing paths unless separately classified with evidence: a failed SQLite operation can represent real storage/media/permission trouble, and `quick_check` corruption is not automatically proof of caller error. Do not broadly convert `Error::Sqlite` or `Error::Invalid` to rejection. The available observation proves one malformed byte-file case only, not all corruption variants or I/O faults.

**One narrow next step:** add a restore-source-validation mapping for only SQLite's `SQLITE_NOTADB` primary result (at the CLI boundary or a small typed core variant), then add one deterministic CLI regression asserting refusal code/message and unchanged source plus absent destination/stage. Keep native GUI acceptance pending because the desktop currently has no database-restore flow.
