Settings' provider, effort and helper segmented controls write directly into `ThreadsUi.settings` (`crates/brn-desktop/src/threads_tiles.rs:1547-1577,1627-1680`). That field is loaded from persisted `Workspace::settings()` at construction and on every `refresh` (`threads_ui.rs:445-447,778-785`). The Models section has a distinct **Save settings** button that calls `configure` (`threads_tiles.rs:1685-1708`); `configure` reads text inputs and writes the full `self.settings` struct through `workspace.configure` (`threads_ui.rs:3535-3555`). This establishes the accepted explicit-save boundary for these form values; the release instructions likewise tell users to click Save after choosing provider/model/effort/auth path (`docs/development/preview-release.md:27-29`).

There are two paths that bypass that boundary. A successful Copilot connection event clones the entire mutable `self.settings`, sets the Copilot provider and credentials directory, then saves the whole struct (`threads_ui.rs:2719-2727`). The chat toolbar's explicit model and effort actions also clone this same struct and persist it wholesale (`threads_ui.rs:2228-2265`). Thus, for example, selecting **High** in Settings without saving and then completing **Connect GitHub Copilot** can persist that unsaved effort as a side effect. Selecting a toolbar model/effort can also commit other form selections. This does not require the normal chat run to consume draft state: `Workspace::prepare_thread_run` reads canonical persisted settings (`crates/brn-threads-app/src/run.rs:89-96`). The defect is that another action persists a draft the user had not saved.

The view also renders the chat model/effort pills from `self.settings` (`crates/brn-desktop/src/threads_writing.rs:732-774,917-923`), so unsaved segmented choices can appear active even though ordinary run preparation still uses canonical settings. Navigating with `show_tile` calls `refresh`, replacing that struct with canonical values (`threads_ui.rs:974-982`), which drops those segmented draft selections without a notice. Text inputs are separate `InputState` entities, so this can leave a mixed-looking form after refresh. This is the same ownership conflation; I did not expand the audit into unrelated Settings sections.
