Before editing, the initial driver, implementation note, and review were preserved at `/tmp/brn-public-restore-interruption/baseline-before-review-fixes/`; their original SHA-256 values are recorded in `SHA256SUMS`.

Receipt persistence failure changes the in-memory outcome to `failed_evidence_persistence`, emits an stderr fallback, and returns nonzero; it cannot leave the user-facing summary labeled qualified.

The preflight checks the frozen CLI artifact SHA-256 `242b141ce518f0ff87d58f7e36b3250269c344211d1552a3d96206cfc62e5f7d` and the checked-in qualification receipt binding it to source `28fd581ea8451ecd95d899248132b62c8f890d03`. It uses pinned main205 SHA `0016b21057b44fa9a64cef2d77d4ae09e317f540`, not a mutable alias. It requires an empty diff over `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, and the verified non-Desktop CLI dependency closure (`brn`, `brn-ai`, `brn-threads-core`, `brn-threads-app`, `brn-threads-intake`, `brn-intake`, and `brn-retrieval`) from source28 to main205 and from main205 to actual HEAD. It also refuses staged, working, or untracked changes on those paths. The receipt records the compared paths and both commit identities.

Ordinary public CLI commands have a 60-second deadline. Each attempt is appended to the receipt before launch; stdout and stderr are continuously drained to task-owned prefix files capped at 64 KiB each, with full-stream byte counts and SHA-256 values. Failures, timeouts, capture errors, actual exits, and elapsed times are retained before the driver stops. The child is always handled through its own `Popen` object in `finally`. The environment inherits existing variables except provider/account key families; only `TMPDIR` is set to a task-owned temporary directory. The inherited `HOME` is left untouched.

The workload uses a fresh canonical absolute root whose parent has at least 2 GiB free. It creates one test workspace via `init --purpose test`, one deterministic Unicode Note of at most 8 MiB via `note-create --text-file`, and a source backup via public `backup`. The source backup limit is 128 MiB and the task-root checkpoint limit is 512 MiB. It first performs one ordinary public restore to `complete-restored`, captures the exact path/type/mode/size/SHA-256 tree, and later confirms every entry is unchanged after the interrupted restore and retry.

There is one selected interrupted-restore `Popen` launch and at most one SIGKILL signal attempt. It observes only exact stage-prefix directories below its fresh destination parent for at most ten seconds. An observed stage must contain more than 1 MiB of database/WAL bytes and more than 1 MiB but less than the source-backup size in staged workspace bytes. If the child finishes or the observation window expires, the driver stops without retry. After the one signal attempt, it waits/reaps separately and requires actual SIGKILL termination, an absent final path, and post-kill partial bytes at the same exact observed stage before retry. Cleanup may wait/reap again after a failed wait, but it never sends a second signal.

Only after that retained partial-stage proof does the driver perform one public restore retry. It checks abandoned-stage removal, source backup hash, source workspace snapshot and marker, sibling sentinel, complete file tree equality with the earlier successful restore, all read-only SQLite schema/logical rows, exact Note UTF-8 bytes, and the documented `workspace_profile` purpose/changed-at normalization. The synthetic fixture must have no edit-session bindings.

Every output-drain thread must finish successfully, and the final receipt must persist successfully, for a run to report qualification or exit zero. A drain, cleanup, tree check, or receipt write failure makes the result nonqualified and exits nonzero; receipt persistence failure is also reported directly on stderr. The driver does not build, access providers/accounts/models, use network access, or modify repository files. A successful run would qualify only one public CLI interruption and retry on this synthetic fixture; it would not establish power-loss behavior, hardware reliability, GUI behavior, owner acceptance, or release readiness.
