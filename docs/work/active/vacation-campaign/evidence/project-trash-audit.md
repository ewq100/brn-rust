# Project deletion and Trash recovery audit

**Result: scoped no-findings.** I found no valid-input defect or consequential missing boundary witness in the selected Project/Trash path. Inspection only; no source, docs, Git state, builds, tests, native interaction, account, or network actions were performed.

## Trace and evidence

- The Projects menu opens a destructive dialog from the selected active project. At dialog creation it captures `project_delete_preview`; the title is derived from current records, and the UI displays the captured removal and retained sets. Enter is explicitly inert; only the danger button's click/Space submits. On service error the dialog remains open and reports that nothing moved and the preview must be refreshed. See `crates/brn-desktop/src/threads_projects.rs` (`projects_menu_section`, `project_delete_dialog`) and `crates/brn-desktop/src/threads_projects_tests.rs` (`projects_primaries_follow_the_view_and_trash_restores_from_active_and_trash`, `project_delete_dialog_confirms_only_by_space_on_its_danger_button`).
- The app service routes the approved preview to the Store. Core recomputes it against current rows and rejects any difference before writing. The preview's snapshot hashes the full removed, retained, and unfinished-action records, so intervening project, linked-note, or dependent-record edits invalidate approval. The restore button closes over the selected trashed project's current version; core rejects a different Trash version. See `crates/brn-threads-app/src/projects.rs` and `crates/brn-threads-core/src/projects.rs` (`preview`, `project_delete_preview`, Delete and Restore arms).
- Existing app witness `stale_preview_and_changed_trash_fail_atomically_without_losing_records` posts a new chat message after preview, verifies deletion refusal, then edits a trashed exclusive Note and verifies restore refusal while project/chat remain archived. This exercises both stale deletion membership and stale linked-Note recovery protection.
- Shared-note behavior has both a native UI witness (`linked_document_survives_project_delete_and_trash_restore`) and service-level coverage in `crates/brn-threads-app/tests/projects.rs`: the deletion test asserts a shared Note remains active, an exclusive Note is trashed and restored, later Note content survives restore, and task choices retain their intended state. The UI witness confirms the project link is restored and the owner's unsent draft remains.
- Project deletion's checked core path interrupts affected Working Runs, increments their fences, pauses the queue and clears its pending dispatch, preserves a displayed partial response in the same write, and routes ended-run attention through the normal helper. `native_project_delete_preserves_displayed_partial_and_pauses_even_an_empty_queue` exercises a live lease, cancellation token, partial transcript, interruption notice, paused queue, and a late worker completion that does not unpause it. `killed_run_candidate` also exercises app-level delete/restore of a real stopped run and verifies the lease removal, attention/review retention, and additional restore fence.
- Restore semantics are explicit in the Trash view (`RESTORE_LINE`) and implemented as selective recovery: only records at their recorded deletion version are restored; changed ones fail without consuming Trash. The app project test verifies shared writing and action choices; `a_deleted_project_hides_its_chats_and_restore_returns_them` verifies hidden chat/search scope returns after restore. Kept-outside Actions and cancelled tasks are not implicitly reversed.

## Scope note

The desktop suite does not appear to simulate opening the delete dialog, mutating a linked Note, then submitting that stale dialog and asserting the dialog-level error text. This is already protected and atomically witnessed at the checked service boundary by the app test above; I do not judge an extra UI mirror test consequential for this audit. Native usability/owner acceptance was not observed and is not inferred.
