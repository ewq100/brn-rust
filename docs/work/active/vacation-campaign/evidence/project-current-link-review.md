## Requirements lens

The native Project document picker already excludes archived and superseded Notes (`crates/brn-desktop/src/threads_projects.rs:843–850`), but its captured rows can outlive a subsequent supersession. Its click handler sends the saved Note ID through `apply_project`/`Workspace::project_command`, without automatic replacement following. Current chat-record enumeration also excludes superseded Notes (`crates/brn-threads-core/src/context.rs:211–224`). Therefore a direct or stale picker LinkDocument must recheck that saved identity's current metadata at the shared mutation boundary.

The added core guard (`crates/brn-threads-core/src/projects.rs:493–499`) does exactly that: after resolving an active saved Note, it refuses only LinkDocument when `superseded_by` is set. It emits a concise correction without naming or following a possibly differently scoped replacement. An unsuperseded Note still follows the existing linking path. UnlinkDocument bypasses this new condition and retains its existing active-Note/private-retention constraints; no new ability to unlink archived or exclusively private retained documents is claimed.

The behavior paragraph (`docs/architecture/threads-behavior.md:84`) expresses current unsuperseded admission and original-ID unlink without imposing automatic retargeting, historical migration, a new versioned command shape or refresh framework. Existing links and Note provenance are not rewritten by the added branch. A merely renamed Project would not establish this Note-lifecycle defect and is not used as the justification.

## Correctness and ownership lens

Both ordinary and converging public app routes enter the same `Store::project_command_body`; the CLI's project-link route uses the converging entry, while native uses the ordinary entry. A WithProgress wrapper is unwrapped before the command match, so it cannot bypass the guard. The rule is centralized in the existing core owner operation, with no duplicate UI/service policy implementation or new layer.

The operation starts an SQLite Immediate transaction, verifies the bound request, replays an existing committed receipt, then reads current records (`projects.rs:337–365`). The guard executes in that same writer transaction before Project mutations, affected-run fences, progress messages, preparation or Apply. A competing supersession cannot slip between the check and this operation's write; later supersession remains ordinary later state and does not retarget a prior link. An invalid new link rolls back its mutation transaction without partial Project writes, fences, receipts or history changes.

There is one important evidence distinction: app entry points reserve/bind the operation identity before entering this transaction (`crates/brn-threads-app/src/projects.rs:11–20`, `converge.rs:60–76`; core `store.rs:267–306`). A refused request can therefore leave its existing-style bound operation allocation. The test's unchanged records and receipt history are accurate; they must not be reported as byte-identical whole-database/no durable allocation. This behavior is unchanged by the candidate and preserves stable identity across an uncertain preparation/retry boundary.

Receipt replay is checked **before** the new current-state guard. Repeating the original already-applied LinkDocument under its identical key therefore returns its prior receipt even after the Note is later superseded; it does not create a fresh link or silently replace identity. Reusing the identity with different command content still fails the binding check. New attempts against a superseded identity refuse before convergence/no-op detection, consistent with selected admission behavior. Existing generic Undo/compensation remains unchanged, rather than becoming a new lifecycle admission framework. Privacy scope, protected data, exact UTF-8/revision bytes, schema and command serialization are untouched.
