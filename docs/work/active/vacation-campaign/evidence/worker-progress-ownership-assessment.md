The operation-specific `progress: String` is ambient in `ThreadsUi`, but it is a presentation slot for the one current `Worker`, not an independently scheduled status channel. The worker owns an operation kind and its own receiver; Run identity remains immutable on `WorkerOperation::Run` (`threads_worker.rs:40-72,93-147`). `ThreadsUi` owns the visible label and funnels all operation events through the current worker's receiver (`threads_ui.rs:2692-2697,2732-2748`). This is a modestly broader state shape than a progress value embedded in each `Worker`, but source does not establish an observable ownership failure or enough cleanup duplication to justify migration.

## Observed lifecycle and consumers

- **Run callbacks and identity.** The provider callback maps tool/budget progress to `WorkerEvent::Progress` over the newly created channel; text/activity events share that receiver (`threads_ui.rs:1978-2017`). The host installs the Run worker, then sets “Starting…” (`:2046-2065`). Stop and Stop-and-Send retrieve the current worker's Run identity before checked persistence; ordinary stop also uses the current partial stream (`:2080-2118`, `:2650-2681`). Run progress is associated with the identity's chat for `RunActivity`, while the visible label updates only from this drained event (`:2732-2748`). The current chat status consumes it through `worker.kind().status(&self.progress)` (`threads_chat.rs:22-31`). Writing's live-progress bar first requires a writing worker for the displayed note; its view gets the same label (`writing-ui/src/workbench.rs:46-53,72-76`; host passes `worker.run_identity()` and `progress` at `threads_ui.rs:4380-4384`).
- **Terminal batch and replacement.** `Worker::drain` admits events only through the first `Finished`, `RunFinished`, or `Converted` event (`threads_worker.rs:223-256`). The host consumes a terminal while the old worker is still installed, then clears `worker`, stream and progress (`threads_ui.rs:2780-2854`; import terminal clears worker/progress at `:2905-2922`). Any dispatch/continuation starts after the full terminal batch (`:3001-3010`); a new Run sets its own initial status after installing its worker (`:2053-2065`). Separate receivers mean later old-worker sends cannot become events on the successor's channel. This is a source-structure inference; no race stress or provider behavior was exercised.
- **Import.** Import progress is emitted by the conversion callback through its worker's captured sender, followed by `Converted` (`threads_ui.rs:3252-3300`); startup sets intent-specific text (`:3302-3314`). Only a reference import whose captured context is displayed renders this label in writing setup (`writing-ui/src/setup.rs:315-329`). The `Converted` event is terminal, and the label is cleared before the synchronous checked import/attachment effect (`threads_ui.rs:2905-2922,2924-2997`). No delayed import status path was found that survives worker retirement.
- **Export/backup and connect.** Export/backup produce only a terminal `Finished` on their dedicated worker channel; initial text and their durable completion/status fields are set in the starter/terminal paths (`threads_ui.rs:3441-3488`, `:2851-2885`). Connect similarly sets its starting label after worker installation and sends login/connected/models/terminal events through its own channel (`:3490-3616`; login updates the visible text at `:2760-2777`). Completion clears the common progress value before refreshing. No overlapping worker can start through the shown import/output/connect starts because each checks `self.worker` before launching (`:3110-3120`, `:3441-3445`; Run start has its own dispatch/queue path).
- **Disconnect.** A disconnected receiver is preserved through the current operation's failure handling before worker/stream/progress retirement (`threads_ui.rs:3023-3038`). For Run, this retains the immutable identity through partial preservation; the progress label itself is not persisted as canonical work state.

## Prior evidence accounted for

The supplied `run-partial-ownership-design.md` recommended keeping partial answer text host-owned and avoiding a second RunSession because existing Run identity and a small number of cleanup sites already give it a coherent lifetime. The `2026-10-20-run-preview-audit.md` likewise found no consequential navigation/completion defect and treated RunActivity as the owner of live/retained Run activity. This assessment does not reopen those decisions: it checks the separate operation-progress label. RunActivity labels and durable Run progress are distinct from this transient `ThreadsUi.progress`; neither should be conflated with it.

## Decision and limits

Keep the current host-owned progress slot. Its consumers are operation-aware via the current worker, start paths initialize the slot, and terminal/disconnect paths retire it with that worker. Moving it into `Worker` would add accessors and require migrating the status, writing preview, Run stop/cancel labels and every importer/exporter/connect starter without demonstrating a concrete invalid state removed. A generalized worker session/reducer would duplicate operation identity and lifecycle machinery. No production route or implementation-only tests were identified for retirement.

This is a source assessment, not proof of every scheduling interleaving or native rendering. The most meaningful revisit trigger is a demonstrated stale label/operation mismatch, an additional independent progress producer, or repeated cleanup growth. If that happens, first consider a narrow `Worker`-owned operation label tied to the existing operation enum, while retaining host presentation; current evidence does not support doing that now.
