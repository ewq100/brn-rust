# Embedded PNG retention — bounded pre-research

## Finding

**Capability: yes, at the pinned SDK level.** Local registry source for Xberg 1.3.10 has a direct DOCX route that reads embedded package bytes when `ImageExtractionConfig.extract_images` is true and places them in `ExtractedDocument.images[].data`. No model, provider, network request, or package acquisition is needed for this route. This is source inspection only; I did not run the alternative config on the fixture or qualify a retained-image subprocess call.

**Production path today: no.** The shared stock and BRN helper config sets `images: None`, `captioning: None`, `qr_codes: Some(false)`, and embedded-image OCR off. The supported CLI setting exposes only converter (`xberg`/`xberg-brn`) and AI (`on`/`off`), not an image-retention control. The actual archived CLI attempt imported the synthetic `footnotes.docx` with its 13,308-byte inline PNG and returned zero Assets, two image-byte gaps, and an unresolved `media/image1.png` link. That is direct evidence about the current config, not a negative finding about SDK capability.

The local registry implementation matches the pinned source-map anchor: `xberg-1.3.10/src/core/config/extraction/core.rs` SHA-256 `fd9e2afd7b0fc3153e5984d96e6618691b6648ccb388b002f4f6c7e6b6f77142`, equal to source-map entry X37. The helper lock pins registry Xberg 1.3.10 with checksum `f9859ca06d9ee171c65c91cfbb0a25287a45622e7628f1b45ba5353b473b6f0d`. No external lookup was needed.

## Exact route and constraints

- `ExtractionConfig::needs_image_data()` is true for explicit image extraction, captioning, QR detection, or OCR on embedded images. The DOCX extractor uses that predicate before resolving the embedded relationship, opening the archive member, and reading it into `ExtractedImage.data` (`Xberg core/config/extraction/core.rs:1127-1146`; `extractors/docx.rs:1087-1121,1123-1144,1164-1184`). The public result type carries raw bytes plus format, index, optional dimensions, and source path (`types/extraction.rs:185-191,834-897`). Xberg's own DOCX source test constructs `images.extract_images=true` (`extractors/docx.rs:3074-3094`), but that test's assertions are about image nodes/placeholders, not retained bytes from the present BRN fixture.
- An offline, no-model trial can set only `images.extract_images=true` while keeping OCR globally disabled, embedded-image OCR false, `run_ocr_on_images=false`, captioning absent, and QR detection false. Current helper configuration already has `disable_ocr=true`, `ocr=None`, `force_ocr=false`, `ocr_embedded_images=false`, and `captioning=None` (`tools/xberg-intake-helper/src/engine.rs:17-24`). The SDK image config's OCR-on-image default is true, so explicitly turning it off in the test-local configuration avoids ambiguity (`xberg/core/config/extraction/types.rs:479-499`). When image extraction is enabled the DOCX extractor forces Markdown and defaults placeholder injection on; BRN already requests Markdown, and the existing projector then relocates placeholders (`xberg/extractors/docx.rs:849-856`; `tools/xberg-intake-helper/src/engine.rs:8-12`). The helper uses `ExtractInput::from_bytes` and denies local-file inputs/file URIs (`engine.rs:59-75,42-46`); its restricted process denies network and inherited filesystem access (`crates/brn-intake/src/helper_runtime.rs:52-59,90-100`). Embedded bytes come from the DOCX ZIP member, not remote Markdown URLs.
- Current helper security config uses request-derived `e = max_expanded_bytes` for Xberg `max_archive_size` and `max_content_size` (both 16 MiB by default), file-count cap 512, and the other `SecurityLimits` at `engine.rs:28-40`. Xberg's DOCX parser also has 100 MiB per-member and 500 MiB whole-archive hard declared-size checks, with the DOCX image read capped at 100 MiB and read at most `declared_size + 1` before discarding an over-declared member (`xberg/extraction/docx/mod.rs:26-31`; `xberg/extraction/docx/parser.rs:2135-2197`; `xberg/extractors/docx.rs:1102-1121`). The helper's configured 16 MiB aggregate archive limit is tighter than that DOCX-wide ceiling. Its `max_compression_ratio` is also assigned `e` (16,777,216), so this is not a tight ratio cap; `max_embedded_file_bytes=16 MiB` concerns separate embedded attachments, not the DOCX picture loop. These are existing boundaries, not evidence to silently change them. This bounds accepted aggregate package bytes; it does not establish a per-process RSS ceiling.
- BRN projection retains only nonempty PNG results with dimensions, hashes the returned bytes, creates `asset-<sha256>` identity, derives a hash-based PNG filename, and relocates matching image Markdown destinations. Empty bytes and non-PNG formats become gaps; it never fetches source paths or external links (`tools/xberg-intake-helper/src/project.rs:54-89,90-110`). A relevant correctness question is that Xberg's DOCX width/height come from the drawing extent (`extractors/docx.rs:1123-1136`), while `DocumentExtraction::validate_for` decodes the actual PNG and requires those dimensions to match (`crates/brn-intake/src/document.rs:125-151`). The fixture trial must check this rather than silently substitute dimensions.
- Downstream limits are explicit: input 16 MiB; expanded/decoded 16 MiB; 512 package parts; 32 assets; 16 MiB total retained image bytes; 32 Mi pixels per image and 64 Mi total pixels; output 64 MiB; helper request protocol maximum 64 MiB (`16 MiB * 4 + 1 KiB`); default host wall time 5 s, maximum 30 s (`crates/brn-intake/src/lib.rs:8-18,34-47,50-78`). The intake host caps subprocess stdout at 64 MiB and transient storage at input+output (80 MiB by default), monitors cancellation/deadline, and kills/reaps the process group (`crates/brn-threads-intake/src/documents.rs:99-117`; `crates/brn-threads-intake/src/process.rs:14-18,75-151`). macOS installs deny-default sandboxing with CPU 10 s, 64 descriptors, and 64 MiB file-size limits; Linux x86_64 also has a 1 GiB virtual address-space limit. The maintained README explicitly says no hard heap/RSS ceiling is claimed (`crates/brn-intake/src/helper_runtime.rs:90-129`; `helper_runtime_linux.rs:233-249`; `crates/brn-threads-intake/README.md:17-22`).

## Policy, provenance, and compatibility

The existing helper tests deliberately enforce the current published-defaults policy: `all_non_security_sdk_options_keep_published_defaults` compares the whole config with `ExtractionConfig::default()` after removing only the declared host/execution/security overrides; `images` remains part of that comparison (`tools/xberg-intake-helper/tests/eight_kinds.rs:287-316`). The ordinary eight-kind fixture assertion also requires zero projected Assets (`eight_kinds.rs:60-85`). Turning images on in the shared config would change both stock and BRN helper behavior and would invalidate those assertions; preserving compatibility does not authorize rewriting them to accept the new behavior.

Projection and host provenance are content-bound: the response retains source SHA-256 and backend; the host verifies engine identity and source hash; each image gets a content-derived SHA-256 ID/name; persisted intake creates a linked Asset and rewrites the Note to `brn-asset://…` (`tools/xberg-intake-helper/src/project.rs:72-85,115-125`; `crates/brn-intake/src/document.rs:9-43,104-111`; `crates/brn-threads-app/src/intake.rs:329-335,450-469`). The original document remains external and the Source locator/hash remain the provenance for its contents; the asset is the retained derived image bytes.

A compatibility concern is that the current `engine_identity` binds Xberg version/source and, for the BRN variant, accepted patch hashes; it does not bind the helper's extraction configuration (`crates/brn-intake/src/document.rs:9-43`; `tools/xberg-intake-helper/build.rs:4-26`). If production starts retaining images under that same identity, otherwise identical converter labels could describe different output policy. A test-local experiment can keep the fixed identity out of accepted records. Any production default or user-selectable policy needs an explicit decision about compatibility and provenance identity.

## Smallest qualification and decision

A minimal offline engineering qualification is one isolated test using the existing synthetic `footnotes.docx` bytes and a test-local Xberg config that enables only image extraction. Assert the raw SDK result contains the expected nonempty PNG bytes and source occurrence, then pass it through the existing projector and `DocumentExtraction::validate_for` to check content hash, media type, dimensions, hash-based filename/link relocation, duplicate references, and all current byte/pixel/count/output bounds. Preserve the existing default-policy tests unchanged. If this local witness passes, the next separate qualification is to exercise the same test-only policy through the existing restricted helper subprocess and intake host budgets; do not claim that an in-process SDK witness proves sandbox/process behavior.

No product decision is needed to run that nonpublishing synthetic qualification. A product decision is needed before changing shipped behavior or adding a CLI/desktop control: current supported settings only select converter and AI, the defaults policy is explicitly tested, and retained Assets change ordinary output and storage. The single tiny fixture is enough for a bounded capability witness, not a general Office/PDF image-fidelity claim or proof of resource safety at every input limit.
