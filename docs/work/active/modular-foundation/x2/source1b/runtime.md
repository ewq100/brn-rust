No runtime is implemented or executed here. All paths below refer to the exact checksum-verified xberg1.3.10 source under the registry root in package-ledger.json; source anchors are also indexed in source-anchors.json.

Chosen prospective operation: `xberg::extract(ExtractInput::bytes(...).mime_type(exact_admitted_mime), &config)`; one bytes input; no batch, URI, file, source-supplied path, child-document auto-extraction, model, cache, OCR or custom processor. Set `extraction_timeout_secs=None` explicitly. The external process deadline/PGID termination remains authoritative; it does not undo parsing or make Tokio blocking tasks cancellable.

## Finite proposed helper thread budget (requires separate allocation and real proof)

Xberg core/config/concurrency.rs697–738 builds the global Rayon pool once, using `ConcurrencyConfig.max_threads`. Set **Some(1)** on the FIRST and only extraction in a fresh helper. No model session pools. Default pool initialization failure is only logged upstream; prove no earlier codec/other initializer won the global pool, and fail qualification if the intended thread bound is not demonstrated. No new BRN global registry or direct Rayon dependency is proposed. PNG/image JPEG paths inspected use serial decoders; image parallel iterators are enabled by rayon. Saved metadata also lists ravif/rav1e threading descendants through a weak optional edge, although image avif is OFF; static feature traversal excludes that branch. rav1e api/config/mod.rs261–267 can create its own ThreadPoolBuilder(num_threads), so any future AVIF enablement would need its OWN finite thread disposition, not an assumption the Xberg global pool controls it. Neither AVIF nor additional codecs are admitted. Native rendering source did not expose its own production threadpool. Asset admission remains PNG/JPEG with predecode dimensions/decoded-byte checks; emitted codec/thread paths still need runtime evidence.

For the later combined PDF+Excel helper propose `Builder::new_current_thread().max_blocking_threads(2).thread_stack_size(16*1024*1024).build()` then **one** `block_on` of the bytes future, constructed after existing restrictions and request admission. No enable_all/IO/time drivers for a None-timeout/no-URI operation. These are maintained Tokio1.53.2 builder APIs (builder.rs261/570/680/1072), not code added now. Main/helper thread runs the future; max2 is a conservative finite ceiling allowing a blocking stage plus one independently queued initialization stage. The inspected native closure is synchronous and pipeline initialization is serial after it; no nested blocking-worker-await cycle was found in this selected path. This is not proof all feature-enabled paths need at most2; any newly reachable nested worker requires a new source/runtime qualification before admission. Do not blindly set1 or reuse Xberg's unbounded/default process-global sync-wrapper runtime (core/runtime.rs, compiled only for other model features).

Proposed maximum **5 concurrently existing application threads** in the selected one-job profile:1 main +up to2 Tokio blocking +1 Rayon +1 joined HTML conversion. This is a source-based configuration target, not an OS-enforced thread or RSS cap. Initializer and PDF may reuse blocking threads; count both regardless. Rayon default worker stack and OS main stack must be measured/recorded;16MiB is the proposed Tokio/known HTML stack, not a claim all stacks are16MiB or memory committed in full. Thread creation, CPU10/NOFILE64, syscall/file attempts, observed peak threads/RSS/latency and bounded shutdown must be exercised under the **unchanged real restricted executable for every admitted kind**. Started Tokio blocking work cannot be aborted by dropping a future; bounded runtime shutdown/process kill+wait owns exit, no hard-RSS/remote-Undo claim.

PDF-only or HTML-only **no-Tokio** profiles can retain source-consistent std-Wake/None pending actual helper proof; they still initialize the explicitly limited Rayon pool. HTML is already in X1's closure and adds no package or Tokio requirement. This sequencing does not exclude native Excel from the approved all-document objective.
