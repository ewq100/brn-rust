## Feature-unified invocation/runtime prerequisite

For PDF-only no-tokio closure, explicit None timeout and existing std-Wake single-input pattern are source-consistent; actual restricted helper remains unexecuted. Before **any** feature addition, repeat real helper schema1/2/runtime/sandbox/resource qualification for **every already admitted kind**, and record effective features, threads and operation path.

`excel` enables tokio-runtime, including target-native process/fs/rt-multi-thread. Some timeout would immediately need a timer. With None, normal Excel single-input path at extractors/excel.rs398–418 invokes `read_excel_bytes` directly when `is_batch_mode()==false`; `spawn_blocking` occurs only in the batch branch. DOCX/PPTX also have conditional batch paths. Public `extract` delegates one `extract_one` with batch scope false; `extract_batch` sets/spawns batch scope ([src/engine/extract_impl.rs:177](/Users/evokessler/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/xberg-1.3.10/src/engine/extract_impl.rs:177), [src/engine/extract_impl.rs:1090](/Users/evokessler/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/xberg-1.3.10/src/engine/extract_impl.rs:1090)). This is evidence that runtime is **not proven unavoidable**, not proof that every downstream all-format path is synchronous. Audit all exact1b implementations/call paths, set None explicitly, use no batch/URI, then qualify actual helper under feature union. If any admitted operation truly needs Tokio, request exact helper-local runtime/dependency/thread/CPU/sandbox allocation before enabling; do not blindly add runtime or use excel-wasm as a native dodge.
