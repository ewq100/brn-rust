# Independent review — combined BRN foundation candidate

Read the canonical modular-foundation plan, contracts/ownership/baseline, A/B/C evidence, current repository authority and the lead's exact combined candidate ref. Review the **actual combined tree**, not only three separate branches or their reports.

You are independent and read-only by default. Do not change implementation, merge, publish, release, access owner data or call paid models unless separately assigned. Synthetic offline checks may be run in an isolated worktree. Report exact commands and limitations. Do not accept another agent's passing-test summary without checking material evidence.

## Review objectives

1. **Product fit:** Is the writing milestone (master plan section 17) complete inside BRN on current components? Within one writing context, do references and the brief persist across chats and restart, with document-local feedback/review and Chat closed? Is the active context shown and resolved by the shared service, never an arbitrary linked conversation? Does the development host reuse the same implementation and real shared service?
2. **Real modularity:** Trace dependencies. Ensure writing is not secretly a wrapper around the full desktop/workspace: `brn-writing-ui` must not depend on `brn-desktop`, and run start and active-writing-context resolution must come from the shared service, not copies in desktop, CLI and host. Check that the default workspace build on Linux compiles no GPUI (F22). Intake and retrieval remain reusable behind narrow interfaces. Reject duplicated storage, permissions, context membership, provider clients, saved-operation Undo or parallel writing implementations.
3. **Safety contracts:** Trace every changed write/read path to shared authority. Check the section 7.2 binding table: setup edits make the candidate stale; ordinary reference edits remain applicable with "changed since"; required-current material needs Refresh; access loss refuses Apply. Also test stale document/protection/scope changes, dirty generations, exact candidate binding, replay after lost responses, cancellation-before-save, grouped atomicity, local-vs-durable Undo, private provenance, v1 request and saved-candidate compatibility, and restart/backup behavior.
4. **Information scope:** Search/exact reads/source panes/assets/snippets/counts/cursors/Connections/caches/traces use the same host-owned scope. Historical citations do not defeat access revocation. Confirm, with the test evidence and not by assumption, that owner-review Apply of a writing candidate rechecks the visibility of its `Historical` reference inputs. Confirm that no earlier approval or automatic retry applies a candidate after access loss (the CW2 gate). Under F21, a setup, brief, reference metadata or reference private to one scope never appears in another scope's UI previews, request capture or run. Private material applied to a shared note is disclosed in review. Source content cannot expand tools/provider/permissions.
5. **Source fidelity:** Full import has independently checked expected content or honest gaps. Table/figure association is verified, not just word presence. Original files are not secretly retained. Sources used reflect actual supplied/read retained revisions. Import coverage, retained text read and requirements reported as checked are shown separately; none claims full original-file coverage or verification of every requirement. Top-k retrieval is not labeled exhaustive reading.
6. **Dependency decisions:** Inspect the X1 and Z1 reports and their section 17 status (passed, failed, blocked, pending or deferred; Z1 stock compatibility separate from any adaptation). Check exact pins/features, package versus upstream workspace differences, GUI/native runtime graph, licenses/provenance, build/maintenance footprint and mandatory qualification failures. Confirm no experiment code reached production paths without a separate approved cutover. Negative adoption decisions are valid. Neither marketing nor successful demos prove qualification.
7. **Baseline behavior:** Dedicated conversion behavior is preserved or explicitly superseded with evidence. Existing model selection, delegated maintenance, projects/private scopes, queue, recovery and supported import formats have not regressed incidentally.
8. **Tests:** Check the applicable F01–F22 cases against the master plan section 13 registry. Retrieval checks match the affected behavior. Relevant tests assert actual outcomes and are not zero-test/self-skipped/mocked-only substitutes. Required native and Linux core contexts remain meaningful. Mutation survivors and performance/retrieval comparisons have honest interpretation. No relaxed threshold or deleted test hides a regression.
9. **Cleanup and compatibility:** Retired routes are gone after qualified cutover; no hidden fallback or duplicate policy remains. Necessary saved-data readers survive. Schema changes, backups and code/data rollback are coherent.
10. **Evidence:** Distinguish implemented, deterministic/live/native verified, reviewed, owner-accepted, locally integrated, published, merged and released. A locked/unavailable Mac means native gates remain open. Check that the section 17 per-area program status is recorded and that the writing milestone is not presented as completion of the whole foundation objective.

## Output

Lead with blocking/high-severity findings, each with exact file/line, reproducible scenario, violated contract and the smallest coherent fix. Then list medium/low findings and residual unverified risks. Classify each as a confirmed defect, evidence gap or design trade-off; do not inflate preferences into defects.

Give a clear verdict: ready for the next stated gate; ready only with named limitations; or not ready with explicit blockers. State which checks you actually ran. Do not authorize a release or claim untested usability.
