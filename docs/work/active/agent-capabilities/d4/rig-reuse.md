# Pinned reuse and boundary evidence

Inspected actual cached `rig-rmcp-0.44.0/src/native.rs`: `McpTool::from_mcp_server(...).with_timeout(...) -> DynamicTool` preserves native MCP structured/context metadata and bounds each request by polling a cancellable SDK request handle. On deadline it explicitly sends cancellation with a bounded1s grace. BRN must keep this future polled instead of assuming caller drop cancels it.

R0 actual proof (`experiments/r0-rig-reuse/src/mcp.rs`) showed100ms SDK cancellation, dynamic list refresh and disconnect retirement; local task abort and disconnect each left a controlled remote handler pending for200ms. D4 must fence late acceptance and never claim remote processing undone. R0 used duplex, not HTTP or BRN data grants.

Inspected rmcp2.2 `StreamableHttpClient` and `StreamableHttpClientTransport::with_client`: supported seam for exact-destination and fresh dispatch checks. Defaults have unlimited exponential SSE retries and expired-session replay, so BRN disables both. Stock SDK reqwest client disables redirects but JSON/error/SSE response reads are not bounded. A narrow policy HTTP adapter is needed to cap response bytes before SDK typed decoding/parser; no new JSON-RPC/agent driver. SDK owns handshake, request IDs, sessions, cancellation and DynamicTool conversion. Descriptions/raw SDK errors are untrusted and cannot be logged verbatim.

No existing maintained general JSON Schema validator was found in locked/cached sources; schemars generates schemas but does not validate JSON. Proposed usable first subset uses fixed typed empty-object/query contracts and exact advertised-schema identity, not a keyword interpreter; all other schemas explicitly unsupported pending principal disposition.

Actual implemented SDK seam: `StreamableHttpClient` POST/GET/DELETE use a no-proxy, no-redirect reqwest client with exact URI equality; raw HTTP entity-body chunks (including SSE comments/framing and error/event/chunk data) are cumulatively bounded before maintained `sse_stream::SseStream`/typed SDK decoding. This is not a bound on HTTP headers/TLS overhead or a provider-token proof. The SDK exports boxed SSE/error aliases but not the parser constructor, justifying the separately allocated direct existing-version parser dependency.

Actual synthetic SDK tests now observe server cancellation tokens for Stop, SDK absolute deadline and dropped caller, with explicit controlled release and client drain before disconnect. This distinguishes continued polling of the SDK cancellation future from the R0 caller-abort negative. These are intermediate source-labelled checks, not external-server behavior or remote Undo proof.

`InitializeResult` is bounded and hashed only as self-reported metadata; matching it cannot attest the anonymous server implementation. Changed metadata is refused before reviewed-input dispatch. Canonical policy/trace keeps digest identities only, never server instructions as system authority. A model-authored saved reply may legitimately quote received material; tests of no raw input/tool-result automatic archive do not promise that no such quote can ever occur.

Additional actual SDK boundary coverage: an observed tool-list-change notification retires the snapshot before a controlled pending result is accepted; subsequent invocations refuse without a second tool call. Notification coordination uses a private cfg(test)-only Notify seam; production still uses its original retirement flag. Both exact Empty and Query contracts have actual SDK HTTP invocation witnesses. Unknown Empty fields refuse before dispatch.

Pinned reqwest0.13.5 `retry.rs:11–12,86–89` and `async_impl/client.rs:1409–1412` document its protocol-NACK default and maintained opt-out. The adapter now explicitly selects `retry::never()` as well as SDK NeverRetry. No controlled low-level NACK was reproduced; ordinary HTTP errors/no-extra-tool-call counts are not claimed as that behavioral proof. A genuine acknowledgement-header witness failed before correction (bodyless202 with Location accepted); common response policy now runs before202/204 Accepted and for GET/DELETE, preserving valid bodyless acknowledgements and no recipient request.

The actual normal workspace build's supported Cargo compiler-artifact output records rmcp features `client`, client-side SSE, streamable HTTP reqwest client and the accepted upstream defaults (`server`, macros/base64/async-rw). It omits child-process, transport-io and streamable-HTTP-server transport. The maintained SDK/axum test-server graph is separately recorded. This unit/build evidence, not dev-unified metadata alone, qualifies the normal feature distinction; no BRN serve/listener route exists.
