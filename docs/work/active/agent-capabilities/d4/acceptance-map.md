## Supported limits and recovery

One anonymous literal-loopback HTTP endpoint, one selected approved tool and one exact reviewed input per prepared Run. General permits general nonprivate chats; exact Chat binding can authorize a standalone private chat; Project binding permits that current active Project context. Canonical Project chats use BRN's existing private-context predicate. Scope movement and current policy/fence are checked again at dispatch. Owner status is a control surface; contextual metadata is filtered without exposing other-scope access rows/counts.

Bounds are host application limits:8 tools,32KiB aggregate catalogue,4KiB metadata/tool,2KiB schema/tool,8KiB encoded arguments,2048 UTF-8 query bytes,32KiB text result,256KiB cumulative raw HTTP entity-body bytes before decode, concurrency1 and absolute deadlines. They are not model-token proof, HTTP-header/TLS bounds, or a remote side-effect guarantee. Existing whole-request estimates and132KiB encoded-result admission are separate backstops.

`server_digest` pins bounded self-reported InitializeResult metadata. Same metadata cannot attest implementation identity or prevent endpoint replacement. The owner approves known behavior; readonly annotations cannot prove it. Unsupported auth/remote/DNS/proxy/redirect/rich content/schema/transport cases fail honestly. No server instructions become system authority.

Request and SDK retries/expired-session replay are disabled. Reqwest's maintained protocol-NACK opt-out is explicit source/config evidence; a low-level NACK was not reproduced. Already-sent remote processing may finish after Stop/disconnect. A missing/stale/expired exact grant is visibly unavailable and requires a new explicit owner authorization on a fresh prepared invocation, without automatic query reuse.
